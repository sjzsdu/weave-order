## Q1 · 移动端（Taro：H5 + 小程序 + App）包含哪些功能

**现状事实**

- **Taro 不存在。** 全仓无 `taro` / `react-native` 依赖（`package.json`、`apps/web/package.json:13` 依赖清单只有 React + Radix + Zustand）。
- `apps/web` 是**单页应用，连路由都没有**：`vite.config.ts` 只配了 `/api` 代理（`:8`），没有 `react-router`；三个窗口是 Radix Tabs 切换（`App.tsx:71`）。
- 所以 README 里"Web + H5 按路由区分"（`README.md:17`、`apps/web/package.json:5`）目前**只是说法**：H5 既没有路由，也没有独立的移动布局。
- 现有 UI 在手机上的实际形态：三列按钮栅格（`IntentBar.tsx:184`）、宽表格（`Panorama.tsx:65`）、抽屉式审批弹窗（`ReviewQueue.tsx:191`）—— 能用，但都是桌面密度。

**规划建议**

移动端不是把桌面搬过去，按"人在哪、手边有什么"切：

| 角色        | 场景                   | 移动端该有的                                                                         | 不该有的           |
| ----------- | ---------------------- | ------------------------------------------------------------------------------------ | ------------------ |
| 业务员      | 客户现场 / 展会 / 路上 | 拍照找样（T-001）、查该客户历史价（T-003）、看自己的待办、现场建寄样单（运单号后补） | 批量录入、模板编辑 |
| 老板 / 主管 | 通勤、饭局             | 审批（看摘要 + 明细 + 一键批/驳）、金额看板、异常提醒                                | 全景宽表、审计流水 |
| 跟单        | 仓库 / 快递点          | 扫码录运单、改寄样状态、拍签收单                                                     | 报价编辑           |

技术路径（按成本从低到高）：

1. **先抽 `packages/api-client`**。现在 `apps/web/src/api.ts:36` 是写死的相对路径 `fetch`，移动端（尤其是 App / 小程序）需要绝对 base URL + token 注入。不先抽这一层，Taro 接进来要复制一遍。
2. **先做 H5**（复用现有 React 代码，改响应式或做"单窗口模式"），验证"移动审批 + 拍照找样"是否真被用。
3. **Taro 一次三端是伪省钱**：`packages/schema` 是纯 Zod，可以三端复用；但 `apps/web` 的 Radix + Tailwind + DOM 组件一个都复用了不（小程序无 DOM）。等于 UI 重写一遍，还要额外吃小程序审核、包体 2MB 限制、登录态差异。
4. **拍照找样的硬约束**：T-001 现在走 base64 JSON，上限 8MB 契约（`packages/schema/src/tools/t001-search-fabric-by-image.ts:18`）、服务端 body 10MB（`main.ts:13`）。手机原图轻松超，必须先压缩或改直传对象存储 —— 这是移动端的前置条件，不是优化项。

**待用户拍板**

1. 移动端首要用户是谁（业务员 / 老板 / 客户）？三者是完全不同的产品，不要合成一个。
2. 现在投，还是等 Web 报价链路跑通再投？（我的建议：后者，除非"老板在路上批单"已经是成交瓶颈。）
3. 小程序是不是必须？如果**客户**也要用（自助查价、查寄样进度），那是第二个产品，权限模型和界面都要重做，不该混在内部工具里。
4. 铁律 #4「只有三个窗口」怎么套到手机上：我建议"移动端只呈现三窗口里的 1–2 个"，而不是新增业务窗口。

## Q2 · 桌面端（Web + 桌面）包含哪些功能

**现状事实**

- **无 Electron / Tauri**，全仓无相关依赖。
- 只有 `apps/web` 一套 Web UI：三个窗口（`App.tsx:10`、`:85`–`:93`）。
- **生产环境没有前端托管路径**：API 不 serve 静态文件（`apps/api/src` 中搜不到 `ServeStatic` / `sendFile`），`vite.config.ts` 的 `/api` 代理只在 dev 生效（`:8`）。也就是说现在即使 `vite build` 出了 `dist/`，也没有任何东西负责把它发给浏览器。

**规划建议**

先把"桌面端"这个词拆开，因为它混了两件事：

| 需求                                 | 归属                     | 理由                                   |
| ------------------------------------ | ------------------------ | -------------------------------------- |
| 大屏看全景、多标签、快捷键           | **Web**（加 PWA 可安装） | 浏览器就够，装壳只增加升级负担         |
| 报价编辑、批量改、Excel 导入导出     | **Web**                  | 文件读写用 File System Access API 足够 |
| 打本地打印机、扫码枪、电子秤、扫描件 | **桌面壳**（唯一刚需）   | 浏览器拿不到这些设备                   |

因此建议的产品形态是 **Web 为主 + 一个只做本地桥的桌面壳**：

- 桌面壳（Tauri，不是 Electron：安装包小一个数量级、不打包 Chromium、内存低）里**不放业务 UI**，只暴露本地能力：`print(pdf)`、`scan()`、`readFile()`。业务页面依然从 Web 加载，壳只做桥。
- 这样避免"两套界面"——那是维护成本翻倍的经典死法，改一个按钮要改两处。
- 时间点：**阶段二**（打印、批量导入）才需要，阶段一不需要。

**待用户拍板**

1. 有没有必须**离线**使用的场景（展会无网、工厂无网）？有的话，本地缓存/离线报价就是另一个技术方案（IndexedDB + 冲突合并），成本高很多。
2. 是否需要读本地 Excel / 扫描件？
3. 有没有指定的打印机 / 标签机型号？（决定 Q6 走 A4 还是热敏）
4. 桌面壳你能接受的安装方式：静默安装（IT 统一推）还是用户自己下载？

## Q3 · agent 出了内容，人类不满意怎么改

**现状事实**

- **改稿能力为零。** `controllers.ts` 12 条路由里没有任何 `PUT` / `PATCH` / `DELETE`（`grep "@Get\|@Post\|@Put\|@Patch\|@Delete"` 实测）。
- 内核没有任何"修改草稿"的方法：`QuoteService` 只有 `generateDraft` / `getDraft` / `confirmDraft` / `rejectDraft`；`ShipmentService` 只有 `createDraft` / `getById` / `confirm` / `reject`（`apps/api/src/kernel/quotes.service.ts`、`shipments.service.ts`）。
- 界面只有批准 / 拒绝两个动作（`ReviewQueue.tsx:120`–`:135`），弹窗里最多填一个驳回备注（`:213`–`:224`）。
- **改的窗口期极短**：`getDraft` 强制 `status === "DRAFT"`，否则抛 `INVALID_STATE_TRANSITION`（`quotes.service.ts:185`）。一旦批准，连读都读不出来，更别说改。
- 驳回 = 直接置 `REJECTED`（`quotes.service.ts:284`），想改只能从头再生成一份，旧的留在账本里当噪声。
- 文案类产出（跟进话术）根本没落库，只在检查点里（`followup-graph.ts:135`），人连"改"的入口都没有。

**规划建议**

这是**阶段一的阻塞项**——不能改的报价，业务员不会用第二次。分三种改法，按频率排序，分三批做：

| 类型   | 例子                                                | 内核动作                                                                                                                                | 优先级 |
| ------ | --------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | ------ |
| 改值   | 单价 15.0 → 15.2、数量 500 → 800、有效期 30 → 15 天 | `reviseDraft(id, patch, ctx)`：DRAFT 内原地改，`version + 1`，重算行金额与总额（**必须内核算**，不接受前端传总额），写审计 before/after | P0     |
| 改结构 | 加一行面料、删一行                                  | 同一接口，`items` 全量替换 + 重算                                                                                                       | P0     |
| 改文案 | 发给客户的话术、报价备注                            | 不进报价单，属于"消息草稿"实体                                                                                                          | P1     |

配套的四个设计决定（建议，需确认）：

1. **改完是不是要重新审批？** 建议：同一人改完可直接批（省一步，符合"一个人负责一单"）；**换人改必须重新走审批**。
2. **每次改都是一次决策增量。** 改价要写进 `customer_contexts.decision_deltas`——这个字段现在有表、有写函数、但全仓零调用（`customers.service.ts:204`）。改稿闭环正好是它唯一的真实数据来源，也是阶段三"越用越准"的原料。
3. **界面形态**：不做"边批边改"。审批卡片 → 展开详情 → 行内编辑 → 保存为新版本 → 再点批准。审批人看到的是"最后一版"，历史版本可追溯。
4. **改价阈值**：改幅超过阈值（如 10%）应升级审批（主管/老板）。这条依赖 Q5 的权限，所以 Q5 不能拖太久。

**待用户拍板**

1. 改稿要不要保留"版本给客户看"（比如发出去的是 v2，客户手里还是 v1）？
2. 改价幅度超过多少必须上级批？
3. agent 的建议被改掉之后，要不要在界面上显示"你改了它的建议"（这是训练数据，也是信任建设，但会增加噪音）？

## Q4 · 桌面端是不是要等有界面操作所有的 tool

**现状事实**

- 5 个 tool（`apps/api/src/tools/index.ts:32`–`:40`）。
- 有 UI 入口的 3 个：T-002 找样、T-004 报价草稿、T-005 寄样单（`IntentBar.tsx:184`–`:207`）。
- T-001 以图搜图**有 HTTP 端点但没有 UI 入口**（`controllers.ts:51`；`IntentBar` 只有三个按钮，无上传控件）。
- T-003 客户历史**连 HTTP 入口都没有**（`tools/index.ts:26` 定义了，`controllers.ts` 里搜不到路由），UI 更没有。

**规划建议**

**不要按 tool 铺界面。** 判断标准不是"覆盖率"，而是"这件事人要不要做决定、要不要在决定时看到证据"：

| tool 类型 | 例子                                   | 界面策略                                                                                                                           |
| --------- | -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 只读查询  | T-001 找样、T-002 匹配、T-003 客户历史 | **不单独做界面，但结果必须出现在人做决定的地方**。T-003 嵌进审批详情（"这客户上次报 15.0"）；T-001 嵌进"建寄样 / 找样"流程（拍照） |
| 产草稿    | T-004 报价、T-005 寄样                 | 必须有审批界面，这是铁律 #2 的落地                                                                                                 |
| 高风险    | 未来：改价、删除、批量发送             | 必须有人工确认点 + 审计                                                                                                            |

反模式要明确拒绝：**每个 tool 一个按钮** → 界面退化成工具清单，用户还得学 5 个工具怎么用，等于把"agent 代劳"退回"人选工具"。现在的 Intent Bar 三个按钮已经是这个苗头了。

结论：界面数量由**决策点**决定（当前 3 个：派发 / 审批 / 概览），tool 由**能力**决定（会继续增加）。两者不是一一对应。

**待用户拍板**

1. 要不要给管理员一个"直接调任意 tool"的调试面板（排查问题有用，但绕过 agent 且可能写账本）？建议：只读 tool 开放，写 tool 不开放。

## Q5 · 公司化：内部员工权限怎么分配和控制

**现状事实**

- 身份只有两个值：`actor.type` 是 `"HUMAN" | "AGENT" | "SYSTEM"`（数据库枚举 `packages/db/src/schema/enums.ts:34`；校验点 `quotes.service.ts:207`、`shipments.service.ts:151`）。
- **没有员工概念**：`packages/db/src/schema/` 下只有 `audit / customers / embeddings / enums / quotes / samples` 七类文件，没有 `users` / `roles` / `tenants`。
- 审批人写死：`HUMAN_CONTEXT = { type: "HUMAN", id: "web-approver" }`（`context.ts:12`–`:14`），审计里所有人都是同一个人（`audit.ts:37` 只落 `actorId` 字符串）。
- 没有数据归属：客户表没有 `ownerId`（`packages/db/src/schema/customers.ts:21`–`35`），谁都能看到全部客户。
- 接口无鉴权 + CORS `origin: true`（`main.ts:11`），局域网内任何人都能批准。

**规划建议**

最小 RBAC，三层，缺一层都不成立：

1. **身份层**：`users` 表（id / 姓名 / 手机 / 角色 / 状态）+ 登录。先做企业微信扫码或邮箱密码，**不做 SSO**（Casdoor 之类留到私有化交付时）。会话里的用户 id 替换 `context.ts:12` 的常量。
2. **角色层**（建议 5 个，不要更多）：老板 `owner` / 主管 `manager` / 业务员 `sales` / 跟单 `merchandiser` / 只读 `viewer`（财务先并入只读+导出）。
3. **数据范围层**（最容易出事的一层）：`own`（只看自己客户）/ `team`（看本组）/ `all`。纺织贸易里客户是业务员的命，**跨人可见会直接引发抵触**，默认必须是 `own`，共享要显式授权（"客户交接/协作"功能）。

再加两条必须现在就设计的：

- **审批金额阈值**：`sales ≤ 5 万`、`manager ≤ 20 万`、`owner 无上限`（数字待定）。这条一旦上线再改要重写审批流，所以要在阶段一就留好字段。
- **审计快照**：审计里除了 `actorId`，还要落 `actorRole` 与 `tenantId` 快照。否则员工调岗/离职后，历史审批无法还原"当时他有没有这个权限"。

多租户：**现在不做，但现在决定字段**。加 `tenantId` 列便宜（单租户填默认值），后期拆库极贵。建议在 `customers` / `quotes` / `sample_shipments` 三张主表先加。

**待用户拍板**

1. 角色就这 5 个够不够？财务要不要单独角色（能看金额不能改单据）？
2. 谁能看别人的客户？有没有"团队/小组"这一层（决定 `team` 范围存不存在）？
3. 审批金额阈值定多少？
4. 业务员离职怎么交接（客户/在途报价/寄样）——这个流程不做，第一个离职就会出事。

## Q6 · 远程打印：打印客户端怎么弄，格式怎么个性化

**现状事实**

- **零实现。** 全仓搜不到 `print` / `pdf` / `puppeteer` / 相关依赖；`print`/`pdf` 只出现在 README 的规划文字里。
- 报价批准后不产出任何文件，只改状态（`quotes.service.ts:219`）。
- 没有模板系统，没有对象存储，没有文件表。

**规划建议**

把"打印"拆成两个独立问题，**不要一起做**：

**A. 格式个性化（模板）**

- 模板 = HTML + CSS + 变量占位，存数据库（按 `tenantId` + 单据类型），版本化。
- **变量只能来自内核视图**，模板里不允许写业务逻辑（否则模板即业务逻辑，绕过内核）。变量清单由后端提供，模板只能引用。
- 渲染用服务端无头浏览器（Playwright）→ PDF。渲染结果与模板版本一起存档，保证"当时打出来是什么样"可还原。
- 编辑体验：第一版只做"选模板 + 填变量（公司抬头、银行账号、条款）"，可视化拖拽编辑器放到以后。

**B. 远程打印（客户端）**

- 服务端只负责：生成 PDF → 入队 → 记录状态（`QUEUED / PRINTING / DONE / FAILED`）。
- **打印代理**跑在办公室一台常驻机器上（小主机/前台电脑）：注册到服务端 → 长轮询或 WebSocket 取任务 → 调本地驱动（Windows 打印 API / CUPS）→ 回报结果。
- 关键点：**代理必须独立于任何人的电脑**。挂在业务员笔记本上，他一合盖全公司打不出来。
- 先做降级方案：**生成 PDF + 浏览器打印**（零客户端），验证格式需求真实存在后再做代理。很多"远程打印"需求，本质是"导出 PDF 发微信"。

**待用户拍板**

1. 打印什么：报价单 / 寄样单 / 合同 / **箱唛标签**？（标签是另一个世界：热敏机 + ZPL/TSPL，排版逻辑完全不同）
2. 打印机型号与连接方式（网络 / USB）？谁日常维护加纸换碳带？
3. 谁维护模板：IT 还是业务自己改？
4. 打印要不要留痕（谁打的、打了几次、哪一版）？如果报价单外发要控数量，这条就是刚需。

## Q7 · 如何一键部署

**现状事实**

- `docker-compose.yml` 只有 `postgres` + `redis` 两个服务（`:2`、`:19`），**没有 app 服务**。
- **无 Dockerfile**（仓库根与 `apps/*` 下都没有）。
- **无 `.github/workflows`**（无 CI）。
- API 不托管前端静态文件；dev 靠 Vite 代理（`vite.config.ts:8`），生产没有网关配置。
- 迁移靠手动 `pnpm db:migrate`（`package.json` scripts），应用启动不会自动迁移。
- 健康检查只有 `GET /api/health`（`controllers.ts:18`），且只探数据库（读一条审计，`:21`）。

**规划建议**

按"部署给谁"分三档，**先做 A**：

| 档                          | 场景         | 形态                                                                                                                                                   | 成本 |
| --------------------------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ---- |
| **A. 单机 compose**（先做） | 自用 / 试点  | `docker compose up` 起 nginx(web) + api + pg + redis；迁移用一次性 job（`service_completed_successfully`）；`.env` 模板 + 首次引导（建租户、建管理员） | 低   |
| B. 云托管                   | 小团队正式用 | 一台 VM + Caddy（自动 TLS）+ compose；`pg_dump` 定时备份到对象存储；日志收集                                                                           | 中   |
| C. 私有化交付               | 客户内网     | 离线镜像包（`docker save`）+ 安装脚本；必须无外网可跑（LLM/embedding 得能本地降级——现在默认 `local-stub` 恰好满足）                                    | 高   |

**前置条件（不做这些，"一键"是假的）**：

1. **CI 必须先有。** 没有 CI 的一键部署，部署的是没人验过的代码。至少 `build + lint + typecheck + test`，且**必须带 PG**（现在 19 个依赖 PG 的用例在干净环境默认跳过）。
2. `/api/health` 扩成 readiness：DB + 迁移版本 + provider 可用性（现在只探 DB）。
3. 迁移进启动编排，不能再靠人手跑。
4. 备份与恢复脚本（含"恢复到某天"的演练），这条比一键部署更救命。

**待用户拍板**

1. 部署在哪：自家云 / 客户内网 / 公有云 SaaS？三者运维模式完全不同。
2. 是否需要信创/国产化（麒麟、达梦、人大金仓）？需要的话，PG/Redis 选型现在就要评估。
3. 客户数据能不能出内网？（决定 B 档还是 C 档）
4. 谁负责运维：有 IT 还是你兼着？没有 IT 就尽量往 B 档托管靠。

**阻塞当前可用性的（不能拖到下一阶段）**：人工改稿、真实数据入口、报价出口（PDF）、CI+部署、身份。这五项缺任何一项，"一个真实业务员用它完成一次真实报价"就做不到。

### 一句话判断

这 8 个问题里，只有 **Q3（改稿）、Q5（身份）、Q7（部署）** 是现在就卡住可用性的；**Q4** 是设计原则不是工程任务；**Q1/Q2/Q6** 是规模化之后才该花钱的地方 —— 现在投移动端，等于在一条还不通的链路上再铺一条更贵的链。
