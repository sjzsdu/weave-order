# 可用性提升迭代计划

> 配套评估：`docs/mvp-usability-assessment.md`。本文只给路线与验收口径，不含实现细节。

## 排序原则

一条链路只有在"真实客户的一句话 → 真实客户收到的东西"整段都成立时才算通。因此：

1. **先让一条链路端到端为真，再谈第二条。** 不做"每个模块各补 20%"的事——那会让所有链路都停在 90%，无法被真实用户验证。
2. **链路上任何一环是假数据，整条链就先不算通。** 假物流 + 假回复 + 假 LLM 叠出来的"演示通过"，对可用性没有贡献。
3. **能让人类兜底的地方，先让人类兜底。** 渠道对接（微信/企业微信 API）审批周期长，不阻塞第一阶段：人复制、系统留痕，比系统假装发出去好。
4. **每阶段的验收必须是"一个人做一次具体动作"**，不是"某接口已上线"。验收做不出来，阶段就不算完。

## 假设（用户未指定，这里显式声明；如不成立请直接改）

- 团队 2–3 人全职（后端 1–2、前端 1），每阶段 2–4 周。
- 试点是**一家**纺织贸易公司的**一个业务组**（5–10 人、几十个客户、几百个样品），不是多租户 SaaS。
- 试点期内不接真实微信/企业微信/邮件 API，用"人工复制 + 系统记录"过渡；渠道对接排在链路跑通之后。
- 真实 LLM 可用（有 key、有预算），但不作为第一阶段的硬依赖：第一阶段允许"规则/模板 + 人改"，先把链路跑通。
- 不改架构铁律（内核/工具/草稿/三窗口）。铁律与新需求的冲突在阶段一显式决策，见下。

## 阶段一 · 打通"报价"这条真实链路

**为什么是报价**：它是纺织贸易里频率最高、离钱最近、外部依赖最少的一环。不需要渠道 API、不需要物流、不需要订单表，就能从"客户一句话"走到"客户收到一份报价单"。寄样跟进虽然代码最多，但它天然依赖物流与回复渠道，作为第一条链路会让第一阶段卡在外部审批上。

**目标**：一个真实业务员，用真实客户和真实样品，从粘贴客户原话到产出一份能直接发给客户的报价，全程 10 分钟内完成，且事后能还原"谁在什么时候、按什么价格批了哪一版"。

**范围**（这几项必须同批交付，缺一条链路就不成立）：

1. **真实数据入口。** 客户与样品可新增/编辑（含成本底线），演示数据可归档。内核写入口已存在（`customers.service.ts:83`、`samples.service.ts:39`），缺的是 HTTP 端点与界面位置。
   - 需产品决策：铁律 #4「只做三个窗口、不做逐条录入表单」与"数据必须能进来"直接冲突。本计划建议**不新增第四个窗口**，把"新建客户/样品"做成 Intent Bar 上下文选择器里的内联新增（一个卡片、三个字段），并在审批窗口的异常处理里提供"这条草稿的样品信息不全 → 补齐"的补录入口。
2. **意图 → 草稿要真的过智能体。** 至少一个 agent 入口（`POST /api/agent/intents` 之类）把"客户原话 + 选中样品"翻成 T-004 入参，并解释它为什么这么报价。单价不再来自前端常量（现在写死在 `IntentBar.tsx:59`），而来自内核里的定价策略（成本底线 × (1+毛利率)，毛利率可配、可按客户层级取）。金额仍由内核计算，铁律不变。
3. **审批要看得见。** 草稿详情视图：客户、样品、数量、单价、行金额、总额、毛利率、有效期、报价依据（智能体给的理由）、历史同客户报价。可**改价后再批**，改价与理由必须进审计。
4. **报价要有出口。** 生成客户可见的报价单（PDF 或图片，含公司抬头、有效期、条款），并可记录"已通过某渠道发给某人、发了哪一版、内容快照"。`SENT` 只在有了发送记录之后才写。
5. **最小身份。** 至少能区分 3–5 个真实账号，审批 actor 来自会话而不是常量（`context.ts:12`）。

**验收标准**（可复现，逐条判定）：

- 一个新账号能在不碰命令行、不跑 `pnpm demo` 的前提下，录入 3 个真实客户 + 10 个真实样品（每条 ≤ 60 秒）。
- 粘贴一段真实客户微信原话（如"这款 220g 棉的，要 500 米，什么价"），选一个样品，**一次点击**得到报价草稿，且单价、数量、总额与人工心算一致（±1 分）。
- 审批人能在详情里看到 5 项以上决策依据（明细、毛利率、历史价、有效期、智能体理由），并能改价后批准；改价动作在审计里可查。
- 批准后能导出一份报价单文件，业务员可以直接转发给客户；系统记录"已发送 + 渠道 + 时间 + 版本"。
- 任何一份 30 天前的已批报价，能重新打开并看到完整明细（当前 `getDraft` 只允许 DRAFT，`quotes.service.ts:185` 必须改）。
- 审计能回答："这份报价的单价是谁改的、改成多少、为什么"。

**明确不做**：真实微信 API、订单、物流、以图搜图、多租户。

**风险**：定价策略一旦拍错，后面所有报价都错。第一阶段必须让业务负责人确认毛利率口径（按客户层级？按面料品类？），并在界面里显式展示，不允许黑箱。

## 阶段二 · 把寄样跟进链路从脚本搬进产品

**目标**：一次真实寄样，从"寄出"到"客户回复 → 自动出报价草稿"，全程在页面上完成，不碰命令行。

**范围**：

1. 跟进任务的入口与生命周期：发起一次跟进（选客户 + 样品 + 运单）、待办列表、当前阶段可视化（含"等待客户回复"）、中途失败的可读错误与重试。图已经具备这些状态（`agent/followup-graph.ts:279`、`agent/state.ts:21`），缺的是 HTTP 面与 UI。
2. 中断可视化：检查点里的 `interrupt` 要让用户看见"现在卡在等什么、等谁、等了几天"；支持从任意检查点继续（现在只能 `pnpm demo:followup`）。
3. 跟进建议必须落库并进入审批队列：现在是只存在检查点里的一条字符串（`followup-graph.ts:135`），人根本看不到。建议要成为一张"待发出的消息草稿"，人可以改、批、发。
4. 外部世界的最小真实化，允许人工兜底：运单号由人录入或扫码；物流先接一家可查的（快递100 之类）或允许人工更新状态；客户回复允许"粘贴微信原话"进入 `RawCustomerReply`；LLM 可先用规则，但**必须能替换**且失败可重试。
5. 建议发送渠道先做"复制文案 + 记录已发"，不阻塞在微信 API 审批上。

**验收标准**：

- 5 单真实寄样：从录入运单到"客户回复 → 报价草稿进审批队列"，业务员不需要登录任何开发工具。
- 一次跟进中断后关闭浏览器、隔天再打开，能在页面上看到"等待回复第 2 天"并继续。
- 智能体给出的跟进建议，人能看见、能改、能发；发出后状态从"建议"变"已发送"并有时间戳。
- 图在任意节点失败时，用户看到的是业务语义错误（如缺运单号 → `NO_TRACKING_NUMBER`），而不是 Zod 原文或堆栈。
- 5 单里至少 1 单走完"回复询价 → 报价草稿"，且报价单价来自阶段一的定价策略。

**明确不做**：自动发微信、智能体自主决定发给谁、多轮谈判。

## 阶段三 · 让智能体越用越准（记忆闭环）

**目标**：人对智能体产出的每一次修改，都变成下一次更准的依据。

**现状**：客户上下文的写入函数 `appendDecisionDelta` 全仓无调用方（`customers.service.ts:204`），护城河数据一条都没积累。

**范围**：

1. 审批里的改价、驳回原因、修改备注，结构化写入 `decision_deltas`（字段、原值、新值、理由、客户）。
2. 用这些增量影响下一次建议：同客户历史成交价、常用毛利率、偏好渠道与时间窗，在报价/跟进建议里显式引用（"上次给该客户报 15.0 元/米，本次建议 15.2"）。
3. 建议质量可度量：采纳率、改价幅度分布、驳回率、从回复到报价的时长。

**验收标准**：

- 同一客户第 3 次报价时，智能体建议里出现该客户历史价与偏离说明；人能看到"为什么这次不一样"。
- 每一条被采纳的建议都能追溯到所用上下文，且上下文可纠正（人说"不对，他不敏感"要能改掉）。
- 试点 4 周后能出一张表：建议采纳率、平均改价幅度、驳回原因 Top 3。

**明确不做**：自动学习/微调模型；跨客户的知识迁移。

## 阶段四 · 订单与对账（新领域）

**目标**：报价成交之后的事能进系统，客户历史不再有空洞。

**现状**：订单表不存在，`T-003` 的 `recentOrders` 恒为空（`customers.service.ts:198`），"订单跟踪与对账"在产品描述里但代码里没有。

**范围**：订单实体与状态机（报价 → 成交 → 生产/备货 → 发货 → 收货）、应收与回款登记、对账单生成、逾期提醒。仍然遵守内核/工具/审批三层。

**验收标准**：一张真实订单从报价成交到回款登记全流程可查；客户历史里能看到成交价与履约表现；月底能出一份对账单。

**明确不做**：生产排期、库存、财务总账对接。

## 并行轨道（不占用链路阶段，但必须在阶段一结束前就位）

这几件事不产生用户可见功能，但缺了就没法判断"能不能上线"：

| 事项   | 现状               | 最低要求                                                                                                              |
| ------ | ------------------ | --------------------------------------------------------------------------------------------------------------------- |
| CI     | 无 `.github/`      | PR 上跑 `build + lint + typecheck + test`，且**必须带 PG**（现在 19 个依赖 PG 的用例默认跳过，`http.e2e.test.ts:14`） |
| 部署   | 无 `Dockerfile`    | 一条命令起 API + Web + PG，能给试点客户一个固定地址                                                                   |
| 可观测 | 只有 `console.log` | 结构化日志 + 错误上报 + 一个"这次请求发生了什么"的追踪 id（审计里已有 `correlationId` 字段，`audit.ts:37`，尚未使用） |
| 身份   | 无                 | 阶段一的最小账号体系即可，不做 SSO；但必须先于任何真实客户数据进入系统                                                |

## 阶段与"可用"的对应关系

| 阶段完成后，用户可以…… | 仍然不能……                     |
| ---------------------- | ------------------------------ |
| 一                     | 用真实数据报价并发出，全程留痕 | 寄样跟进、订单、多人协作之外的复杂权限 |
| 二                     | 寄样后由系统提醒并推进到报价   | 订单履约与对账                         |
| 三                     | 感觉系统"记得这个客户"         | 大规模数据（pgvector、分页、检索质量） |
| 四                     | 用一套系统管完从询价到回款     | 渠道全自动（仍需人点发送）             |

## 需要产品负责人拍板的三件事

1. **数据入口放哪**（与铁律 #4 冲突）：本计划建议 Intent Bar 内联新增，不新增窗口。若坚持"零录入表单"，就必须先做 Excel/CSV 导入，否则阶段一无法验收。
2. **定价口径**：毛利率按客户层级、按品类，还是按业务员手动设定？这决定智能体报价建议的可信度。
3. **`SENT` 的定义**：是"人已导出并转发"就算发送，还是必须等到渠道回执？这决定阶段一是否需要提前做渠道对接。
