# MVP 现状与可用性评估

> 评估对象：`main` @ `2d992d1`（feat(step5): 三个窗口 MVP + approval API 与端到端审批）
> 评估方式：完整 checkout 仓库、逐目录读代码（135 个受版本控制文件）、本地安装依赖并跑通 `pnpm test`。
> 未能执行的验证：本地 Docker 不可用，`docker compose up -d` / `pnpm demo` / `pnpm dev` 未实际运行；凡涉及运行时行为的结论，均以代码路径为准并标注证据行号。

## 结论先行

这个 MVP 的**工程骨骼是可信的**：确定性内核、单一写入口、同事务审计、数据库层禁止改写、草稿必须人类确认 —— 这些约束不是文档里的承诺，而是代码和 ESLint 规则强制出来的，`pnpm test` 在干净环境里 53 passed / 19 skipped。

但它的**可用性问题不是"功能还少"，而是没有一条链路能从一个真实客户的一句话走到客户真正收到的东西**。具体是三个断点同时存在：

1. **智能体不在链路上。** 页面上三个按钮是硬编码参数的表单直调工具，唯一的真智能体（寄样跟进图）只被 `scripts/` 和测试引用，产品里没有任何一行代码能触发它。用户在"派发意图"窗口输入的那句话，最终只变成一条备注或一个找样关键词。
2. **账本有进无出。** 写路径（草稿 → 审批 → 生效 → 审计）是完整的；读路径只到"摘要 + 金额"这一层。报价单的明细在确认之后**在系统里读不出来了** —— `getDraft` 强制只允许 `DRAFT` 状态。
3. **外部世界全是占位。** 报价发不出去（无 PDF、无渠道、无发送记录）、物流是运单号哈希、客户回复是预设脚本、以图搜图是把图片字节哈希成 16 维向量。演示能跑，真实业务一碰就断。

再叠加两个产品级冲突：**没有任何真实数据入口**（客户/样品只能靠 `pnpm demo` 造，且造完不可删），以及**审批没有身份**（任何能访问 3000 端口的人都能批准，审计里永远记成 `web-approver`）。

## 二、按用户链路走一遍：卡在哪

以下每一条都是"用户想做一件具体的事"，而不是"某个模块缺什么"。

### 链路 1：把真实客户和样品录进来 —— 走不通

用户想把手上真实的客户和面料录进系统，第一步就停住。

- 内核**有**写入口：`customers.service.ts:83`、`samples.service.ts:39`。
- 但 HTTP 面**只读**：`controllers.ts:34` 和 `:40` 只有 `GET /api/customers`、`GET /api/samples`，全仓没有任何创建客户/样品的端点。
- 唯一的数据来源是 `pnpm demo`：每次运行用 `Date.now()` 后缀新建一条 `DEMO-xxxx` 客户 + `SMP-xxxx` 样品（`apps/api/scripts/demo-kernel.ts:78`、`:96`），**没有清理或归档路径**（无 DELETE 端点，`SampleService` 也没有 archive 方法）。
- 演示脚本还会顺手把自己造的寄样单和报价单直接确认掉（`demo-kernel.ts:140`、`:204`），所以新装环境第一次打开审批窗口是**空的**，用户看不到任何"待办"，也就不知道下一步该干什么。

结论：一个真实业务员在这个系统里**无法拥有自己的数据**，只能看演示数据，且越跑越多。

### 链路 2：向智能体派发一个意图 —— 意图其实是假的

用户以为自己在"跟智能体说话"，实际是一组写死的表单。

- 输入框里的文字只流向两个地方：报价草稿的 `remarks`（`IntentBar.tsx:64`）和找样关键词（`IntentBar.tsx:106`）。没有任何意图解析、没有路由到不同工具。
- 三个按钮的参数全是前端常量：单价 = 成本底线 + 300 分（`IntentBar.tsx:59`）、数量固定 120.5 米（`IntentBar.tsx:68`）、承运商固定"顺丰"（`IntentBar.tsx:90`）。
- 最刺眼的一条：**运单号由浏览器生成**（`IntentBar.tsx:91`，`SF${Date.now().toString(36)}`）。用户要建一张寄样单，系统要求他先编一个运单号，而这个运单号之后会被当成真实物流单号去"追踪"。
- 按钮直接 `POST /api/tools/*`，服务端用固定 `AGENT_CONTEXT`（`controllers.ts:48`、`:59`、`:73`；`context.ts:4`）。**全过程没有智能体进程参与**：`http.module.ts:39` 的控制器列表里没有任何 agent 入口。

结论：所谓"智能体是默认操作者"，在这一层只剩一个按钮的名字。

### 链路 3：审批一份草稿 —— 看不见内容就签字

这是当前产品里最完整的链路，也是最危险的一条。

- 审批卡片只渲染标题、摘要、客户名、时间（`ReviewQueue.tsx:113`–`:117`）。摘要文本形如"1 行 · ¥1,806.00"（`quotes.service.ts:268`）。
- 契约里其实带了 `amountCents` / `currency`（`packages/schema/src/approval.ts:42`），但 UI 没用；**明细行、单价、毛利率、有效期、备注一律看不到**，也没有单条详情接口（`controllers.ts:101`–`:114` 只有 list 和 decide）。
- 没有"改一下再批"。人类只有批准 / 驳回两个动作；驳回即置 `REJECTED`（`quotes.service.ts:284`），想改价只能驳回后从头再来。
- **批完就永久失明**：`getDraft` 强制 `status === "DRAFT"`，否则抛 `INVALID_STATE_TRANSITION`（`quotes.service.ts:185`）。报价单一旦确认，系统里再也读不出它的明细，只剩全景里的那一行摘要。
- 审批人身份是常量：`HUMAN_CONTEXT = { type: "HUMAN", id: "web-approver" }`（`context.ts:12`），配合 `origin: true` 的 CORS（`main.ts:11`）—— 局域网内任何能访问 3000 端口的人都能批准任何单据，审计里还全都是同一个人。

结论：审批窗口在设计上是"人类的唯一决策入口"，在实现上是"盲签 + 无法追查是谁签的"。

### 链路 4：把报价发给客户 —— 没有出口

- 批准把状态改成 `SENT`（`quotes.service.ts:219`–`:224`），但**没有任何东西被生成或发出**：没有 PDF、没有图片、没有可复制的报价文案，没有任何发送渠道调用（全仓搜不到发送函数，"WECHAT" 只作为建议渠道的字面量出现在 `llm.ts:76`）。
- 也就是说，业务员批准之后仍然要自己打开微信、手打一份报价。系统在这一步只留下了一个与事实不符的 `SENT`。
- 同一类问题：`EXPIRED` 在报价状态枚举里（`packages/db/src/schema/enums.ts:26`），但**全仓没有任何代码会写这个状态**，过期报价永远停在 `SENT`。

结论：账本说"已发送"，现实里什么都没发。这是当下最容易让用户失去信任的一点——不是不能用，是**用起来会骗人**。

### 链路 5：寄样寄出后跟进客户 —— 只有命令行能跑

这是产品的差异化能力，目前完成度最高，也最"看得见摸不着"。

- 图是完整的：建寄样单 → 追踪 → 生成跟进建议 → 中断等回复 → 识别意图 → 触发报价草稿（`followup-graph.ts:279`–`:297`），检查点真存在 PG 里（`checkpoint.ts:11`）。
- 但**产品里没有任何入口**：没有"发起一次跟进"的端点，没有待办列表，没有"等待客户回复"的可视化，没有 resume 接口。想让图往前走，只能 `pnpm demo:followup`（`demo-followup.ts:43`、`:97`）。
- 图产出的跟进建议是一条字符串，**只存在检查点里**（`followup-graph.ts:135`），没有落库、没有进审批队列、没有 UI 能看见。用户根本不知道智能体建议了什么。
- 中断之后没有任何提醒机制：谁该去催、什么时候该催，系统不表达。
- 物流是哈希假的（`logistics.ts:32`–`:34`），回复是脚本队列（`reply-source.ts:28`）。

结论：这条链路在演示里成立，在业务里不存在——它的收益（省掉跟进的人力）恰恰是最需要"真的跑起来"才成立的。

### 链路 6：了解一个客户 —— 有工具没入口

- `T-003 get_customer_history` 工具已实现（`customers.service.ts:147`），但既没有 HTTP 路由，也没有 UI，前端 `api.ts` 里也没有对应方法。
- 即使接上，`recentOrders` 恒为空数组（`customers.service.ts:198`），因为订单表还没建；客户历史实际只有"历史报价 + 寄过的样"。
- 全景窗口把客户、样品、单据、审计一次性平铺（`Panorama.tsx:127`–`:191`），没有搜索、没有筛选、没有下钻。

结论：用户无法回答"这个客户以前怎么报价、成交价多少、上次为什么没成"—— 而这正是产品宣称的护城河数据。

### 链路 7：找样

- 参数匹配是"整串 `ILIKE` OR 4 个字段"（`search.service.ts:119`–`:125`），多词查询（"100%棉 220g 现货"）必然零命中；排序分数就是命中字段数 / 4（`:150`），不包含任何业务相关性。
- 以图搜图把图片字节哈希成 16 维向量（`embedding.ts:44`–`:51`），与文本向量做余弦 —— 两个不同空间的哈希噪声比较，结果没有物理意义；而且 `samples` 表连图片字段都没有（`samples.ts:9`–`:26`），系统里根本没有"样品图"这个东西。
- UI 上只有"按关键词找样"一个按钮（`IntentBar.tsx:203`），没有上传图片入口，T-001 在页面上不可达。

结论：找样在演示数据上能出结果，在真实样品库上既搜不准，也无法以图找样。

### 链路 8：多人一起用

- 没有登录、没有用户表、没有角色。AGENT/HUMAN 两个身份都是硬编码常量（`context.ts:4`、`:12`）。
- 所有数据在同一个账本里，没有租户/组织维度；无法区分"张三的客户"和"李四的客户"。
- 前端没有任何轮询或推送，"实时刷新"实际只在本人操作后触发（`store.ts:65`、`ReviewQueue.tsx:84` 手动刷新）。两个人同时用，互相看不见对方的草稿，直到手动刷新。

## 三、可用性低的结构性原因

把上面 8 条链路归并，只有 4 个根因。迭代计划应该直接对着这 4 条打，而不是对着上面 24 个能力项打。

**C1 · 智能体没接在链路上。**
所有页面动作都是"按钮 → 工具"的直连，参数在前端写死。唯一真正的编排（followup graph）只活在脚本里。结果：产品卖的是"智能体代劳"，用户拿到的是一组需要自己填参数的固定表单 —— 智能体的价值（理解模糊输入、多步推进、记住上下文）一点也没交出来。

**C2 · 账本有写入，没有读出。**
写的路径严格、可审计；读的路径只到摘要。单据确认后连明细都读不出来（`quotes.service.ts:185`），没有单条详情接口，没有版本、没有导出。用户没法核对、没法复用、没法追责，账本就只是一个"存了但用不上"的东西。

**C3 · 外部世界全是 stub，且没有人工兜底。**
LLM、物流、客户回复、embedding 四个 provider 的默认实现都是本地假数据，切换真实实现的构造函数直接抛错（`llm.ts:126`、`reply-source.ts:35`、`embedding.ts:60`、`logistics.ts:78`）。同时产品也没有提供"人来补这一步"的入口（比如手工填运单、粘贴客户微信回复、手工上传报价 PDF）。于是一旦离开演示数据，链路必断。

**C4 · 产品铁律与冷启动直接冲突。**
铁律 #4 规定"人类界面只有三个窗口，不做逐条录入表单"（`README.md:183`），但系统没有任何其他数据入口。这不是实现遗漏，是**设计层面的未决问题**：真实客户和样品必须以某种方式进来，必须有人决定它长在哪（Intent Bar 的上下文卡片内联新建？审批窗口的异常处理？还是导入？）。这个决定不做，后面所有链路都无法被真实用户验证。

## 四、必须尽快处理的风险

| 风险                 | 现状                                                             | 后果                                                             |
| -------------------- | ---------------------------------------------------------------- | ---------------------------------------------------------------- |
| `SENT` 语义失真      | 批准即 `SENT`，但无任何发送动作（`quotes.service.ts:219`）       | 账本与事实不符，用户第一次信任就会被打破；后续对账/统计全部失真  |
| 审批无鉴权           | 固定 `web-approver` + 开放 CORS（`context.ts:12`、`main.ts:11`） | 谁都能批准资金相关单据；审计无法追责                             |
| 演示数据不可清理     | `pnpm demo` 每次追加、无删除/归档（`demo-kernel.ts:78`）         | 试用到第三天，全景里全是 `DEMO-xxxx` 噪声                        |
| 关键路径无自动化覆盖 | 依赖 PG 的 19 个用例在干净环境全部跳过（`http.e2e.test.ts:14`）  | 真正跑用户路径的代码（HTTP + 内核）在默认 `pnpm test` 里等于没测 |
| 无 CI / 无部署产物   | 无 `.github/`、无 `Dockerfile`                                   | 无法判断"这次改动是否可上线"，也没有可交付的环境                 |

## 五、本次评估的边界

- 未做用户访谈、未跑真实数据，所有"痛点"都来自代码走查与上述链路推演；哪些痛点在真实业务里更痛，需要在第一个真实试点里校准。
- 未实际启动 `pnpm dev`（本地无 Docker），UI 结论来自代码而非操作截图。
- 未评估性能与并发（当前数据量级下 `list(100)` 全量聚合不构成瓶颈）。
- 迭代计划中的范围与节奏假设，见 `docs/usability-roadmap.md` 的"假设"一节。
