# OCR spike：名片与面料标签字段抽取准确率验证

> 结论先行：**OCR 可以进 P0a，但只能做「预填 + 逐字段确认」，不能做「识别完直接落库」。**
> 推荐路线：**专用 OCR（qwen3.5-ocr）+ 文本模型抽取（qwen-plus）**。
> 在这批 40 张真实照片上，该路线逐字段 exact 准确率 76.3%（3 次运行 74.8%–77.1%），
> 名片「公司+联系人+电话」三要素全对的样本 13/17；面料成分 75.6%。
> 克重、门幅在 20 张标签上从未正确出现，也从未被该路线编造（0/20），因此必须保持人工录入。

## 1. 范围与结论边界

本 spike 回答「识别准确率够不够支撑 P0a 报价闭环」，不写业务代码、不改 `intents`/kernel、不建表。

**做完了**：两条技术路线的可重跑评测脚本、40 张真实照片的逐图真值、逐字段准确率、失败模式、时延与 token 成本、P0a 验收口径建议。

**没做完 / 必须补的**：

- 本批 20 张名片全部来自公开网络（手持、桌面实拍），20 张标签里 15 张是**服装洗水标**，不是面料商/织厂的**米样标签**。标签上没有克重、门幅、批号的正例，因此这三项的准确率**没有被验证**（n=0），只能验证「会不会编造」。
- 需要创始人补 20 张真实名片 + 20 张真实面料/织厂标签（要求见 §10），用同一脚本重跑后替换本文数字。
- 两张设计样卡（占位文案）和一张低分辨率到手写体无法确认的卡被排除在统计外：名片实际计分 17 张，标签按字段分别计分（成分 15 张、含品名 6 张、含批号 7 张、含供应商 16 张）。

## 2. 方法

1. 收集 40 张真实照片（非合成），逐张人工阅读并填写真值，写入 `data/ocr-spike/manifest.json`。真值、来源、失败标签（模糊、反光、手写、多语言、多卡同框等）逐样本记录。
2. 两条路线各跑一遍全量；抽取路线（route-b）重复 3 次，报告均值与波动，避免单次采样下结论。
3. 逐字段对比，不按整图判对错：
   - `exact`：NFKC 归一化、去空白与标点后完全一致；
   - `usable`：exact + 编辑相似度 ≥ 0.9 + 「一方完整包含另一方且长度比 ≥ 0.6」（例如 `TecTake` vs `TecTake GmbH`）；
   - `幻觉`：真值为空但模型输出了内容；
   - 手机/固话额外按「合并可用」统计（名片上两者经常混排，业务只关心能打通）。
4. 时延为客户端墙钟时间，单区域直连，并发 4，不含图片上传。

| 类别          | 张数 | 来源                         | 说明                                                                                         |
| ------------- | ---: | ---------------------------- | -------------------------------------------------------------------------------------------- |

## 4. 两条路线

|            | route-a 多模态大模型直抽                        | route-b 专用 OCR + 文本抽取                          |
| ---------- | ----------------------------------------------- | ---------------------------------------------------- |
| 实现       | `qwen3-vl-plus`，单次调用，直接输出 JSON        | `qwen3.5-ocr` 出纯文本 → `qwen-plus` 按字段抽取 JSON |
| 调用次数   | 1                                               | 2                                                    |
| 可替换性   | 模型即全部，换模型要重新调 prompt               | OCR 段可换 PaddleOCR/RapidOCR 做私有化，抽取段不变   |
| 结构化约束 | 依赖模型遵守 JSON，字段归属容易串（手机进固话） | OCR 文本可回看、可审计，字段归属由文本模型判断       |
| 失败时     | 黑盒，只能看到最终字段                          | 能看到 OCR 原文，便于定位「没识别到」还是「抽错」    |

两条路线使用同一份证据约束 prompt：公司名必须是名片上完整印出的主体、品牌名不算；主营只在明确写出时填；品名/克重/门幅/批号必须有明确标注，品牌名、服装尺码、床品尺寸都不算。

## 7. 成本与时延

|                         |             route-a |               route-b |
| ----------------------- | ------------------: | --------------------: |
| 平均 token / 名片       |              ~1,100 |    ~1,610（OCR+抽取） |
| 平均 token / 标签       |                ~580 |                  ~870 |
| 时延 P50（名片 / 标签） |         3.9s / 3.4s |   4.4–5.2s / 4.1–4.3s |
| 时延 P95（名片 / 标签） | 4.5–6.5s / 4.7–5.1s | 8.9–12.9s / 8.1–14.2s |
| 单张成本量级            |   **0.002–0.01 元** |     **0.002–0.01 元** |

- 成本按「输入 2 元/百万 token、输出 10 元/百万 token」量级估算；实际以阿里云百炼当期价格为准。1000 张图的模型成本在个位数人民币，**成本不是决策因素**。
- 时延才是：route-b 是两次串行调用，P95 明显高于 route-a。移动端还要加上传时间（1–3s/张）。因此 P0a 的 OCR 必须是**异步任务 + 进度提示**，不能阻塞在表单提交上。
- 并发 4 时 P95 被排队放大；生产按租户配额限流，单张预算建议 15s 超时、失败可重试。

## 8. 推荐方案

**采用 route-b（专用 OCR + 文本抽取），OCR 段用 `qwen3.5-ocr`，抽取段用 `qwen-plus`。**

理由：

1. **准确率更高且更稳**：总体 exact 76.3% vs 66.4%；名片电话合并可用均值 89.3%，标签供应商、批号明显更好。
2. **不编造克重/门幅**：route-a 在 20 张标签上编了 2 次克重、1 次门幅，route-b 为 0。报价场景里「编一个克重」比「留空」危险得多。
3. **可维护**：OCR 与抽取解耦。换 OCR（PaddleOCR/RapidOCR 私有化）不影响字段逻辑；出问题能回看 OCR 原文，而不是对着黑盒输出猜。
4. **成本几乎相同**，多一次调用的代价是 P95 时延，已经证明可用异步任务吸收。

route-a 的唯一优势是**公司名**（87.5% vs 75%）。不建议为此上双模型并行（成本翻倍、时延叠加）；先用 route-b，等创始人真实名片跑完，如果公司名仍低于 85%，再加一次轻量二次校验。

**工程落点**：

- 新增无状态 OCR 调用层，输出 `{ text, fields, fieldEvidence, latencyMs, model }`，写 `ocr_results`；`sources` 保留原图。
- `fields` 每个值必须带 `evidence`（原文片段或 bbox/行号）。没有 evidence 的字段一律 `PENDING`，UI 不预填。
- 硬约束：`gsm`、`width`、`business`、`product`、`lot` 默认不自动填；即使用户点「采用建议」，也记一次人工确认。
- 失败/低质图（无文字、模糊、打码）→ `ocr_results.status=NEEDS_INPUT`，UI 直接进入逐字段录入，不展示猜测值。

## 9. P0a 验收口径建议

「关键字段 ≥ 90%」不能整包套用，按字段分层：

| 字段                   | 口径                                                    | 依据                               |
| ---------------------- | ------------------------------------------------------- | ---------------------------------- |
| 联系人、邮箱、职务     | **≥ 90% 自动填，允许用户不改**                          | 实测 97.6% / 100% / 100%           |
| 手机（含固话合并）     | **≥ 85% 自动填，逐字段确认**                            | 实测均值 89.3%，单次最低 85.7%     |
| 公司名、地址           | **≥ 85% 预填，必须逐字段确认**                          | 实测 75% / 91.7%；错一个字就错主体 |
| 成分（面料）           | **≥ 85% 预填，逐字段强制确认**；未达 85% 则整块降级人工 | 实测 75.6%，未达标                 |
| 批号/款号、供应商      | 仅建议值，人工确认后落库                                | 71.4% / 83.3%                      |
| 克重、门幅、主营、品名 | **不自动填**，人工录入                                  | 无正例；幻觉风险高                 |

因此 **P0a 的「零初始化报价成功率 ≥ 80%」需要改写**为：

> 从一张名片/标签出发，用户在不重新输入已知信息的前提下，经**不超过 3 次字段修正**完成客户或样品建档，成功率 ≥ 80%。

这样验收的是「预填省了多少打字」，而不是「模型有多准」，也与本 spike 的数据一致。

**降级方案**（若创始人真实样本上成分仍 < 80%）：

- 纯人工录入 + 原图留存：照片照常进 `sources`，表单空白但可左右对照，用户逐字段填。
- 对 P0a 旅程的影响：建档从「确认 3 个字段」退化为「录入 5–6 个字段」，单张多花约 30–60 秒；不阻塞报价闭环，但「拍照即建档」的体验卖点要降级表述。
- 不建议为了跑分把阈值降到 70% 以下：报价错一个克重/门幅的返工成本远高于让用户多填一格。

## 10. 复现与补样本

```bash
# 1) 把 40 张图片放回 manifest 指向的路径（data/ocr-spike/samples/，已被 gitignore）
# 2) 跑两条路线（需要 DASHSCOPE_API_KEY）
DASHSCOPE_API_KEY=... node scripts/ocr-spike/run.mjs \
  --manifest data/ocr-spike/manifest.json \
  --out data/ocr-spike/runs/$(date +%F)

# 只跑推荐路线、只跑前 5 张做冒烟
DASHSCOPE_API_KEY=... node scripts/ocr-spike/run.mjs --engine route-b --limit 5
```

脚本只用 Node 标准库，不引入生产依赖；输出 `report.md`（逐字段表）、`summary.json`、`predictions/*.json`（含 OCR 原文与每条预测）。

**请创始人补的样本（决定最终验收口径）**：

1. 20 张真实名片：手机拍摄原图，至少覆盖 5 张斜拍/反光、3 张繁体或英文、3 张双面或同框多张。
2. 20 张真实面料/织厂标签：必须包含**克重、门幅、批号/色号、成分、供应商**中的至少三项；不要只给成衣洗水标。
3. 每张图配一行真实字段（可手写拍照），或允许我按图人工标注后回传确认。

放好后重跑同一脚本，替换 §5 的数字即可，不需要改代码。

## 11. 对架构文档的修改建议

1. §8 风险 1「OCR 是最高技术风险」降级为「**OCR 预填可用，全字段自动落库不可用**」；风险重心从「识别准不准」转到「**逐字段确认的交互与审计**」。
2. §5 的 OCR 契约增加 `fieldEvidence` 与 `NEEDS_INPUT`；`ocr_results.fields` 不再允许无出处的值。
3. P0a-3「统一输入」的验收里，把「OCR 成功」定义为「预填字段数 ≥ 1 且用户修正 ≤ 3 次」，而不是「字段全对」。
4. P0a 报价闭环不依赖克重/门幅自动识别：样品建档允许这两项为空，报价时再补，避免 OCR 阻塞主流程。
5. 若后续要做私有化/离线，route-b 的 OCR 段可换 PaddleOCR/RapidOCR，本 spike 的评测脚本可直接复用（只需换一个 `runOcr` 实现）。

## 12. 生产接入（P0a-3 已实现）

生产代码走同一条 route-b：`apps/api/src/platform/ocr.ts`（无状态调用层）→ `kernel/inbound.service.ts`（落 `ocr_results` + 生成理解卡）。prompt 与字段白名单与 §4/§10 的脚本一致，换模型只需改环境变量。

| 变量                | 默认                                                | 说明                                                            |
| ------------------- | --------------------------------------------------- | --------------------------------------------------------------- |
| `OCR_API_KEY`       | 空（回落 `DASHSCOPE_API_KEY`）                      | 未配置时 OCR 显式不可用，任务进入 `NEEDS_INPUT`，不会返回假字段 |
| `OCR_BASE_URL`      | `https://dashscope.aliyuncs.com/compatible-mode/v1` | OpenAI 兼容端点                                                 |
| `OCR_OCR_MODEL`     | `qwen3.5-ocr`                                       | 专用 OCR，只出文本                                              |
| `OCR_EXTRACT_MODEL` | `qwen-plus`                                         | 按字段抽取 JSON                                                 |
| `OCR_TIMEOUT_MS`    | `30000`                                             | 单次调用超时                                                    |
| `OCR_MAX_ATTEMPTS`  | `2`                                                 | 单次 OCR 失败重试次数                                           |

失败语义：
