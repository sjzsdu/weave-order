## 0. 一页读懂

**一句话主张**：纺织贸易公司里，业务的输入应该是"客户的一句话"，输出应该是"客户收到的东西"；中间那一段（查历史、算价、写单、跟进、对账）应该由智能体做完，人只在需要**签字**的地方出现。

**可行性判断（先说结论，理由在第 1 节）**：

| 层次     | 判断                                                                                          |
| -------- | --------------------------------------------------------------------------------------------- |
| 技术可行 | **是，已被代码验证。** 确定性内核、账本不可改、边界机器强制、审批闭环都是能跑的代码，不是设想 |
| 工程可行 | **部分。** 单条链路打通可行；五个端并行不可行。必须一个端一个端解锁                           |
| 产品可行 | **未验证。** 核心价值假设（agent 产出的报价业务员敢直接发）一次都没有被真实检验过             |
| 商业可行 | **有条件。** 做"标杆客户陪跑交付"可行；做"通用多租户 SaaS"在两年内不可行                      |

**最大的三个风险**（第 1.5 节展开）：价值假设未验证（agent 产的东西没人真发过）、数据进不来也归不了人（客户是业务员的私产）、端扩散拖死主线。

**现在有几个端**：**2 个**（服务端 + Web），不是 5 个。移动端（H5/小程序/App）、桌面壳、打印代理**全部为 0**，本文第 3 节逐个标注了 `[0 / 规划]`。

**这套形态最反常识的一条**：功能增长时，**界面不增长**。传统 SaaS 加功能必加界面；这里加能力只加一个 Tool 契约。界面数量由"人的决策点"决定，不随功能数变化。这是后 AI 时代软件最重要的经济性结论（第 2.3 节）。

## 1. 可行性判断

### 1.1 判断口径

"做得成"必须同时满足三条，缺一条就不算：

- **(a) 业务跑得起来**：一个真实业务组能把真实业务跑在里面——数据进得来、钱算得对、结果出得去、事后查得到。
- **(b) 交付撑得住**：2–3 人的团队能交付、能维护、能升级。任何"需要 10 个人才能维护"的设计，在这个项目里等于不可行。
- **(c) 有人愿意付钱**：客户能指出"因为这套东西，我省了谁、省了多少钱、少丢了什么"。

只满足 (a) 是一个好 demo；只满足 (c) 是一个咨询项目；三条同时成立才是产品。

### 1.4 四层可行性结论

**技术可行：是。** 见 1.2。没有未解的技术难题——所有难的部分（确定性内核、审计不可改、边界机器强制、跨进程续跑）都已落地。剩下的都是工程量和产品设计。

**工程可行：部分。** 让一条链路真正贯通，需要五件事同时到位：真实数据入口、报价出口、人工改稿、最小身份、CI 与部署。这五项在 2–3 人团队里是 2–3 个月的事，可行。但**五个端 + 五个链路同时铺，不可行**——这不是悲观，是算术：每多一个端，就多一套构建、发布、兼容、守门人。第 3.7 节把它固化成"一次只解锁一个端"的硬规则。

**产品可行：未验证。** 这是当前最大的不确定性，也是本文最想纠正的认知偏差：现在的问题**不是"功能没做完"**，而是"核心假设一次都没被检验"。一个业务员拿到系统后，第一个判断是"这东西给我的报价对不对"，而这个判断至今没有真实数据。所以下一步不该是加功能，是拿真实客户跑 10 单，看改价幅度。

**商业可行：有条件。** 做"标杆客户 + 陪跑交付"可行：一家公司、一个业务组、可定制的模板与口径，交付重但价值实。做"通用多租户 SaaS"在两年内不可行：每家公司的单据格式、定价口径、审批习惯都不同，而 SaaS 的边际成本优势要求标准化，两者直接冲突。**先做重的、再做轻的**，反了就会死在没有客户的标准化上。

### 1.5 三个最大风险

按"会不会杀死这个项目"排序，不按"好不好解决"排序。

#### R1 · 价值假设未验证：agent 产出的东西没人真发过

**风险**：整个产品的价值主张是"AI 干完整的活"。但今天没有任何一次真实 LLM 参与过报价，页面上的三个按钮是前端硬编码参数直调工具（`IntentBar.tsx:59`、`:68`、`:91`），运单号甚至由浏览器时间生成。也就是说，**产品卖的那件事，一行验证代码都没有**。

**早期信号**：试点第一周，草稿改价幅度中位数 > 10%，或驳回后重做率 > 30%，或业务员开始跳过系统直接手打报价。

**应对（这条最重要）**：把"人改"从失败路径改成**一等公民**。改稿不是一个容错功能，它是本产品唯一的数据来源——每一次改价都是一条 `decision_deltas`，决定第 3 次报价时能不能说"这客户上次 15.0"。所以：

- 改稿闭环必须先于"更聪明的 agent"（顺序反了，agent 永远没数据可学）；
- 审批界面必须显示"依据"，而不是只显示金额（现在连明细都看不到，`ReviewQueue.tsx:113`–`:117` 只渲染标题和摘要）；
- 用改价幅度当作 agent 质量的第一指标，而不是用"生成成功率"。

#### R2 · 数据进不来，也归不了人

**风险**：两个问题叠在一起。技术上，真实客户和样品在微信、Excel、业务员脑子里，格式脏；组织上，客户是业务员的私产，系统里没有 `ownerId`（`packages/db/src/schema/customers.ts:21`–`35`），也没法区分"张三的客户"。一旦业务员发现"我录进来老板就全看见了"，他会选择不录——**系统会因为"太透明"而拿不到数据**。

**早期信号**：系统里的客户数与电话本严重不符；出现"真客户录两个、其余录假"；导入功能被一次性使用后再没人碰。

**应对**：客户归属必须在第一版就有，且默认 `own`（只看自己的）；共享要显式授权（"客户交接"而不是"所有人可见"）。导入先于录入界面（已做：`import.service.ts`），因为 Excel 是业务员**已经在维护**的东西——让他换工具难，让他上传文件不难。

#### R3 · 端扩散拖死主线

**风险**：五个端（Web / H5 / 小程序 / 桌面壳 / 打印代理）每一个都像小项目：构建、登录态、发布、兼容、隐私审核。小团队铺三个端，结果通常是三条链都停在 80%，**没有一条能被真实用户验证**。这个项目最容易犯的错不是做错功能，而是**同时做对太多功能**。

**早期信号**：任何一周同时有 2 个端在开发；某个端上线两周没有任何真实使用记录；PR 开始按端分裂成互不相关的两条线。

**应对**：把"端"从路线图改成**触发条件**（第 3.7 节）：每个端都写清"什么事实发生了才允许开这个端"，并配一条硬规则——**上一端没有跑过真实业务一周，不许开下一端**。

### 1.6 明确说"做不成"的部分

可行性判断的价值一半在"能做什么"，另一半在"别做什么"。以下五条，我判断在可见周期内做不成，或者做成了也不值得：

1. **"客户自助端"（客户登录你的系统查价、下单）—— 12 个月内做不成，也不该做。** 纺织贸易的客户活在微信里，不在你的站点里。让采购注册账号、记密码、登进来查报价，是把摩擦从你身上转移到客户身上，而客户没有理由接受。正确形态：**一条可点的报价链接 / 一张干净的 PDF / 一条结构化消息**，落地页只读、免登录、带签名与有效期。这不是"客户端"，是"输出格式"。

2. **"零审批的自动报价"—— 做不成，且不该尝试。** 报价是承担责任的动作，承担责任不能委托给概率模型。可达到的目标是"agent 出 90%，人改 10% 并签字"，而不是"没人管"。任何试图取消那道签名的设计，都会在第一次报错价时把整个系统的可信度一起赔掉。

3. **"通用纺织 SaaS 多租户"—— 两年内做不成。** 单据模板、定价口径、审批习惯、甚至"报价单上要不要写税号"每家都不同。SaaS 的钱要靠标准化赚，这个行业还没有标准化。可行路径是"标杆客户 → 可复制交付包（含模板库与口径库）→ 单租户私有化"，把"多租户"留到交付包足够稳定之后。

4. **"一个小团队同时维护五个端 + 真实 LLM + 打印 + 离线"—— 工程上做不成。** 见 1.4 与 R3。这不是能力问题，是人月算术。

5. **"以图搜样在真实样品库上直接可用"—— 现在做不成，且原因不是算法。** 向量是 16 维哈希（`platform/embedding.ts:17`），`samples` 表没有图片字段（`packages/db/src/schema/samples.ts:9`–`26`）。真正的前置条件是"样品必须有照片"这个作业习惯——这是产品要推动的行为改变，不是模型选型问题。先解决"拍不拍照"，再解决"搜得准不准"。

**以上五条，如果后续证据推翻，请直接改这份文档的第 1.6 节并注明推翻依据**——这一节的价值在于它会被证伪，而不是它永远正确。

## 2. 后 AI 时代的软件形态

这一节讲的是**主张**，不是实现。判断标准只有一条：这些结论能不能迁移到纺织之外的行业。能迁移，才是"后 AI 时代软件的形态"；不能迁移，就只是本项目的设计偏好。

### 2.1 核心命题：软件的位置变了

> **软件的输入从"人的操作"变成"人的意图"；输出从"界面状态"变成"已生效的账本变更"；中间那层——以前是人的手——现在是智能体。人的位置从"操作者"上移到"批准者"。**

把这个变化拆成四个可检验的断言：

| 断言                  | 传统软件             | 后 AI 时代（本项目的主张）                   |
| --------------------- | -------------------- | -------------------------------------------- |
| 1. 谁在操作系统       | 人（点按钮、填表单） | 智能体（调工具）；人只在例外处介入           |
| 2. 系统记住什么       | 单据（发生了什么）   | 单据 + 上下文（这个人/这个客户为什么这么做） |
| 3. 界面的作用         | 完成操作的场所       | 承担责任的场所                               |
| 4. 功能的增长带来什么 | 更多界面、更多培训   | 更多能力（Tool），界面不变                   |

第 4 条是整个主张的支点，也是唯一一条可以用经济性论证的。

### 2.2 四条铁律：为什么必须是这四条

现有代码里的四条铁律不是风格约定，是对"AI 进了业务系统之后会出什么事"的四道防线。逐条讲透——**注意每一条背后的"如果反过来会怎样"**。

#### 铁律 1 · 确定性内核：为什么账本不能让智能体碰

先说清楚这不是"不信任 AI"。这是**责任不可转移**。

一份报价被发出去，出问题时要有人被追责。这个"人"必须存在，且必须能回答三个问题：谁批的、当时看到的是什么、按什么规则算的。LLM 的输出是概率分布——同一句话问两次可能得到两个价；同一个价，三个月后无法复现它是怎么来的。**让一个不可复现的东西去写一个必须可复现的账，等于在账本里埋了一个永远查不清的洞。**

具体有四个不可让步的点：

1. **可复算**：内核是确定性的，任何一笔账都能用同样的输入重算出来。这是"错在哪一步"能被定位的唯一前提。
2. **可归责**：agent 的行为不可复现，所以 agent 的动作只能以**草稿**形式进入账本；人的 confirm 才是责任锚点。审计里那个 `actorId` 必须是个人，不能是 `quote-agent`。
3. **幂等与并发**：LLM 会重试、会编出不存在的 ID、会被注入。内核用乐观锁（`customers.version`）、唯一约束、事务来兜这些——这些是智能体永远做不对的事。
4. **可执行的价格边界**：成本底线由内核拦（`quotes.service.ts:88`），不写在提示词里。提示词能被人说服，代码不能。

**如果反过来**（让 agent 直接写账）：你会得到一个"大部分时候正确"的账本。而"大部分时候正确"在会计语义上等于"不可用"——因为你无法知道哪一部分是错的那部分。

本项目的关键贡献是把这条**做成了机器约束**而不是文档纪律：`eslint.config.mjs:64`–`140` 让越界 import 编译就红，`apps/api/test/boundary.test.ts` 让它永远红。这是"架构能被守住"和"架构靠自觉"的分水岭。

#### 铁律 2 · 智能体只产出草稿：为什么人只做审批

人的稀缺资源不是时间，是**判断和责任**。而"审批"恰好是这两件事的最小动作：看一眼、改一下、签个名。它不是"操作"，它是**署名**。

这条铁律有三个层层递进的理由：

1. **责任的物理位置**。每个生效动作背后必须有一个具名的人。所以草稿 → 生效之间必须有一道人的动作，且这道动作要留下"我看到了什么"的快照（现在的问题是快照太薄：`ReviewQueue.tsx:113`–`:117` 只显示标题和摘要，人是在看不见明细的情况下签字的）。
2. **人的价值在例外**。agent 做得好的时候人不该出现；人出现，说明这件事有歧义。所以界面的目标不是"让人高效操作"，而是"让人在 30 秒内判断该不该签"。
3. **每次修改都是燃料**。这条最容易被忽略：人对草稿的每一次修改，都是"这个客户/这个品类该怎么定价"的知识抽样。放弃采集它，产品就永远是冷启动。**所以"改"不是失败路径，是主线**——现在这个能力为零（`controllers.ts` 里没有任何 PUT/PATCH，内核没有 `reviseDraft`），这是阶段一最该补的东西。

**如果反过来**（agent 直接生效、人事后追账）：你会同时失去三样——责任主体、训练数据、用户的信任。而且事后的"追账"在心理上等于"纠错"，用户会开始不信任每一次输出。

#### 铁律 3 · 能力即 Tool：为什么不让 agent"操作界面"

最常见的错误路线是 computer-use：让 AI 看截图、点按钮、填表单。它在演示里很神奇，在业务里是灾难，原因是**界面是给人的压缩表示，不是给机器的**：

- **信息编码效率最低**：颜色、布局、"这个按钮看起来能不能点"——这些对人是零成本的线索，对 agent 是需要推理的噪声。
- **脆弱**：改一个 class 名就断。工具契约不会因为 UI 改版而失效。
- **不可验证**：点按钮的结果只能"看起来对了"；工具返回的是结构化数据 + 可判别错误码，可以断言。
- **不可审计**：tool 调用能记下完整入参出参；点击流记不下意图。

所以正确形态是：**每个业务能力 = 一个工具契约**（Zod `.strict()` 输入、可判别失败码、明确前置条件），agent 只能通过工具碰业务。本项目 5 个工具全部如此（`apps/api/src/tools/index.ts:32`）。

这条铁律还有一个常被误读的推论：**界面不需要覆盖所有工具**。工具是"能力面"（会让 agent 能做更多事），界面是"决策面"（只覆盖人需要签字的地方）。两者不是一一对应。

#### 铁律 4 · 人类只有三个窗口：为什么界面不能跟着功能长

先把这条的表述精确化（这是本文对原表述的第一次修订，理由见 5.3）：

> 原表述："人类界面只有三个窗口"。精确化后：**人类界面只有三个决策面**——派发（意图从哪来）、审批（责任在哪落）、全景（信任靠什么建立）。三个决策面不等于三个页面，也不限制端数；它限制的是**决策面的数量**。

为什么是这三个，且只能是这三个：

- 任何一个业务动作，人只有三种参与方式：**提出要求**（派发）、**承担后果**（审批）、**了解全貌**（全景）。第四种"直接操作数据"在 agent-native 架构里没有位置——那是 kernel 和 tool 的活。
- 这条一旦松动，产品就会退化：每加一个功能就加一个页面，最后变成"一个带 AI 按钮的传统 SaaS"。现在的 Intent Bar 三个硬编码按钮（`IntentBar.tsx:184`–`207`）已经是这个苗头的开始——它把"选工具"暴露给了用户。

**这条的经济性推论，也是本文最关键的一句判断**：

> 传统 SaaS 的界面数量 ∝ 功能数量（边际成本线性）；agent-native 的界面数量 ∝ 决策点数量（近似常数）。所以功能增长时，**界面不增长**。

这是后 AI 时代软件相对传统 SaaS 的根本成本优势。它不是"AI 让开发更快"（那是效率提升，10 倍级），而是"AI 让交付物的形状变了"（那是结构性差异，无法追赶）。一家传统 SaaS 想追上，不是加个 AI 按钮的事，是要把"界面即产品"的商业模式改掉。

**但必须诚实**：这条铁律在本项目里有一个真实的、未解决的冲突——"只有三个决策面"和"数据必须进得来"是矛盾的。这个冲突不能靠加第四个窗口解决，正确方向是**让数据的入口不在界面里**：批量导入（已做，`import.service.ts`）、拍照（样品/单据）、渠道同步（未来的微信/邮件抓取）、agent 主动获取。这一步想不清，铁律 #4 会变成产品的天花板。

### 2.3 与传统 SaaS 的本质差别

上面四条铁律合起来，产生七个可观察的差别。这张表可以直接拿去和客户解释"为什么这个不一样"。

| 维度         | 传统 SaaS（含"加了 AI 助手"的） | agent-native（本项目）              | 差别为什么是本质的                       |
| ------------ | ------------------------------- | ----------------------------------- | ---------------------------------------- |
| **操作主体** | 人操作，系统记录                | agent 产出，人批准                  | 决定一切下游设计                         |
| **界面成本** | 界面 ∝ 功能，随规模线性上升     | 界面 ∝ 决策点，近似常数             | 决定毛利结构                             |
| **数据价值** | 操作的副产品（记录）            | agent 的燃料（上下文比单据更值钱）  | 决定护城河是"迁移成本"还是"越用越准"     |
| **审计**     | 事后补的日志（可有可无）        | 账本的构造物（同事务、库层禁改）    | 决定能不能把责任交给人                   |
| **竞争壁垒** | 功能数量 + 客户迁移成本         | 客户上下文的深度 + 建议质量         | 新进入者可以抄功能，抄不了三年的决策记录 |
| **失败模式** | 人不用（学习成本高）            | agent 错得多 → 人不敢批（信任崩塌） | 决定风险管理的重点完全不同               |
| **计价方式** | 席位 / 年费                     | 替代的人力 / 单量 / 减少的损失      | 决定销售话术与续费理由                   |

**最能一句话讲清的差别**：传统 SaaS 卖"更好用的工具"，agent-native 卖"**不用用的工具**"。人从操作里退出，只在例外处出现。所以它的成功指标不是 DAU、不是使用时长、不是功能使用率——**是"人介入的比例在下降，而通过率在上升"**。这两个指标同时变好，产品才在变好；只降介入不提通过率，就是在放权给一个不可靠的东西。

### 2.4 这套形态的代价（诚实清单）

只讲好处的主张不可信。这套形态有四个结构性代价，且每个都必须在产品里被主动对冲：

1. **审批疲劳**。agent 产出质量一般时，人会变成"每天盖 200 个章"的盖章机，判断力反而下降。**对策**：审批队列按风险排序（金额、偏离历史、低于底线）而不是按时间；同类低风险草稿允许批量批（但批量动作本身要更严格的权限）。
2. **黑箱感**。人看不到 agent 为什么这么建议。**对策**：每份草稿必须带"依据"结构（不是一句备注——现在是把理由塞进 `remarks`，`IntentBar.tsx:64`，等于没有）。依据要可追溯到具体数据：哪次历史价、哪个毛利率、哪条上下文。
3. **责任真空**。"系统自动的"是最危险的一句话。**对策**：每个生效动作必须有具名 confirm（现在 `context.ts:12` 是常量 `web-approver`，这是反例，不是实现）。
4. **认知负担转移**。人从"怎么做"变成"这样对不对"，后者更难——因为它要求人真的懂业务。**对策**：不能指望培训解决，只能靠"让对错变明显"：把偏离历史价、低于底线、毛利率异常直接标在卡片上。**这是界面唯一值得投入的地方**。

### 2.5 可迁移的六条结论

如果这套东西成立，它能推广到其他行业的部分是这些（顺序即重要性）：

1. **有账本的地方，确定性内核必须存在，且必须是唯一写入口。** 不是"建议"，是编译期与数据库层强制的。
2. **agent 的能力必须契约化。** 没有 schema 和错误码的能力，无法审计、无法组合、无法回归测试，也就无法交给 AI。
3. **人的投入应集中在责任点，而不是操作点。** 界面数量是成本，不是功能。
4. **数据模型要围绕"上下文"建，不只围绕"单据"建。** 单据记录发生了什么，上下文解释为什么——后者才是 AI 时代的数据资产。
5. **外部世界的每个接入点都必须有人工兜底通道。** 渠道审批周期长、接口会挂、格式会变；"人能手工补这一步并留痕"比"系统假装成功"重要一个数量级（现项目在 `SENT` 上正好犯了这个错，`quotes.service.ts:219`）。
6. **成功指标要换。** 不是使用时长，是"人介入率下降 + 通过率上升"。

## 3. 客户端矩阵

这是本文最该被当作开发依据用的一节。它不只列"哪个端有什么功能"，而是回答三个问题：**这个能力为什么属于这个端**、**哪些能力只允许出现在一个端**、**什么事实发生了才能开下一个端**。

### 3.1 判定原则

端的选择不是偏好问题，是四个约束共同决定的：

| 判据          | 问题                                                           | 决定什么                                       |
| ------------- | -------------------------------------------------------------- | ---------------------------------------------- |
| **P1 现场性** | 这件事必须发生在哪个物理位置？（仓库、展会、客户面前、办公室） | 设备接入（相机/扫码/打印）、网络条件、单手操作 |
| **P2 时延**   | 晚 30 分钟做有没有代价？                                       | 是否必须随身（审批有时延代价，模板编辑没有）   |
| **P3 证据量** | 做这个决定需要同时看多少信息？                                 | 屏幕尺寸与信息密度（一张卡片 vs 一面墙）       |
| **P4 谁在看** | 内部人 / 外部客户 / 机器（无人值守进程）                       | 身份模型、权限、界面语言                       |

由此得到三条**硬规则**，贯穿本节：

1. **一个能力只能有一个"权威形态"。** 同一个能力在别的端只允许"降级形态"（只读、摘要、只批不改）。多个端都能"权威地做同一件事"，必然导致两套实现、两个 bug、两种口径。
2. **端不做业务判断。** 金额怎么算、状态能不能流转、谁有权限——全部在服务端。端只负责"显示什么"和"把人的动作传回去"。任何在端上计算金额、拼状态机的实现都是缺陷。
3. **界面跟着决策点走，不跟着功能走。** 每个端呈现的是"三个决策面"的一个子集（见 2.2 铁律 4），不是一组功能页。

**状态标记法**（全文统一，防止把规划当现状）：

- `[现状]` 仓库里能跑，有代码
- `[现状·残]` 有代码但缺关键一环（有后端无前端 / 有前端无后端 / 只在脚本里）
- `[0 / 规划]` **一行代码都没有**
- `[不做]` 明确判定不做（附理由，见 1.6）

| C18 | 批量导入（冷启动）            |   ●    |  ●  |   ○    |  —  |     —      |    —     |  —  | `[现状]` CLI + `POST /api/import`                             |
| C19 | 部署与运维（健康/备份/升级）  |   ●    |  ○  |   —    |  —  |     —      |    —     |  —  | `[现状·残]` 只有 `/api/health`，无 CI/镜像                    |

> **读表要点**：`●` 只出现在"这件事必须在那里发生"的端。比如 C05 审批在 Web 和企微小程序同时是 `●`——这不是违反规则 1，因为两者的**决策场景不同**（桌前细看 vs 走廊上秒批），且共用同一个决策契约与同一条审计。真正会被规则 1 禁止的是"两个端各有一套审批逻辑"。

### 3.3 逐端详写

#### 3.3.1 服务端 `[现状]`

**定位**：唯一可信的执行体。所有"必须为真"的东西落在这里，其余所有端都只是它的视图与遥控器。

| 能力                       | 说明                                            | 现状                                                            |
| -------------------------- | ----------------------------------------------- | --------------------------------------------------------------- |
| 确定性内核（唯一写入口）   | 业务表写入、金额计算、状态机、审计同事务        | `[现状]` `kernel/index.ts:17`                                   |
| 工具契约（agent 的能力面） | T-001 ~ T-005，Zod `.strict()`                  | `[现状]` `tools/index.ts:32`                                    |
| 审批决策                   | `POST /api/approvals/decide`，HUMAN 上下文      | `[现状]` `controllers.ts:121`                                   |
| 智能体编排 + 检查点        | LangGraph 状态机、PG 持久化、跨进程续跑         | `[现状·残]` 图完整，无 HTTP 入口                                |
| 批量导入                   | 整批原子、逐行可判别回执                        | `[现状]` `controllers.ts:87`                                    |
| 单据详情读接口             | 单条报价/寄样单的完整明细                       | `[0 / 规划]` 只有 list + decide（`controllers.ts:116`、`:121`） |
| 改稿接口                   | `reviseDraft`（version+1、重算、审计）          | `[0 / 规划]` 内核与 HTTP 都没有                                 |
| 身份 / 角色 / 数据范围     | 账号、会话、角色、`ownerId`                     | `[0 / 规划]` 常量 `web-approver`（`context.ts:12`）             |
| 模板渲染                   | HTML+CSS+变量 → PDF，渲染结果与模板版本一起存档 | `[0 / 规划]`                                                    |
| 打印队列                   | 任务入队、状态机、按设备路由                    | `[0 / 规划]`                                                    |
| 发送记录                   | 发给谁、哪个渠道、哪一版、内容快照              | `[0 / 规划]`                                                    |
| 通知调度                   | 待办、超时、异常提醒                            | `[0 / 规划]`                                                    |
| 文件存储                   | 样品图、扫描件、生成的文件                      | `[0 / 规划]` 无对象存储、无文件表                               |

**为什么是服务端**：浏览器不可信（可改前端、可重放请求）、智能体不可信（会幻觉）、办公网不可信（现在是 `origin: true` 的 CORS，`main.ts:11`）。金额、状态、权限三件事只能在服务端判定，这是唯一的选择。

**不应该在服务端**：不做业务界面（除了把 Web 静态产物发给浏览器）；不做"给管理员直接调任意写工具"的调试面板（只读工具可以开放）。

**硬前置**：模板渲染与打印队列必须共用同一份"内核视图"作为变量来源——否则模板作者会开始在里面写 `if` 计算金额，那是绕过内核。

#### 3.3.2 Web 桌面端 `[现状]`（当前唯一的业务界面）

**定位**：证据密度最高、停留时间最长的工作台。今天它是三个窗口的单页应用（`App.tsx:10`、`:71` 用 Radix Tabs 切换，**没有路由**）。

**现状的诚实描述**：三个窗口都有，但都停在"能演示"这一层——审批卡片只渲染标题/摘要/时间（`ReviewQueue.tsx:113`–`:117`），全景是一次性全量平铺（`Panorama.tsx:127`–`:191`），Intent Bar 是三个硬编码参数的按钮（`IntentBar.tsx:59`、`:68`、`:91`）。**没有路由，所以 README 里"Web + H5 按路由区分"（`README.md:20`）目前是说法，不是实现。**

| 能力           | 具体形态                                                             | 现状                                                         |
| -------------- | -------------------------------------------------------------------- | ------------------------------------------------------------ |
| 审批工作台     | 队列按风险排序 → 卡片 → 详情（明细/毛利率/历史价/依据）→ 改价 → 批准 | `[现状·残]` 只有卡片 + 批/驳（`ReviewQueue.tsx:120`–`:135`） |
| 改稿           | 行内编辑、重算、版本、写决策增量                                     | `[0 / 规划]`                                                 |
| 经营全景       | 单据、客户、样品、审计；按客户/状态筛选、下钻                        | `[现状·残]` 只读平铺，无筛选无下钻                           |
| 审计检索       | 按人/单据/时间/动作查，能回答"这单价谁改的"                          | `[现状·残]` 只列最近 N 条（`Panorama.tsx:170`）              |
| 批量导入       | 拖文件、预览校验结果、逐行错误回执                                   | `[现状·残]` 只有 CLI + HTTP，前端无入口                      |
| 成员与权限     | 成员列表、角色、数据范围、审批金额阈值                               | `[0 / 规划]`                                                 |
| 模板管理       | 选模板、填变量（抬头/账号/条款）、预览                               | `[0 / 规划]`                                                 |
| 客户与样品维护 | 编辑、归档、补照片、改成本底线                                       | `[现状·残]` 导入有，单条编辑无                               |
| 寄样跟进看板   | 待办列表、等待回复天数、中断原因、续跑                               | `[0 / 规划]` 图只在脚本里                                    |

**为什么是 Web（而不是桌面壳）**：需要同时看很多列（报价明细、历史价、毛利率）、需要长时间编辑（改价、改结构、批量）、需要多标签与快捷键。浏览器完全够用，装壳只会多一套升级负担。

**不应该在 Web 上**：拍照找样（手机更快、还能现场拍）；扫码录运单（要用摄像头）；离线作业（Web 不该承诺离线，见 3.3.6）。

**硬前置**：抽 `packages/api-client`（现在 `api.ts:34` 是写死的相对路径 `fetch`），否则 H5 与小程序都要复制一遍请求层。

#### 3.3.3 桌面壳 `[0 / 规划]`

**定位**：**只做本地桥**，不放业务界面。业务页面依然从 Web 加载（或离线时用本地缓存），壳只暴露浏览器拿不到的本地能力。

**先做一个关键拆分**（本文对既有规划的第一处实质订正，见 5.3）：`docs/platform-and-engineering-plan.md` 的 Q2 与 Q6 把"桌面壳"和"打印代理"混在一起讲。它们是**两个不同的产物**：

| 维度     | 桌面壳（个人）                                | 打印代理（常驻）                                            |
| -------- | --------------------------------------------- | ----------------------------------------------------------- |
| 跑在哪   | 业务员/内勤自己的电脑                         | 办公室一台常驻小主机（不在任何人笔记本上）                  |
| 生命周期 | 随人开关                                      | 7×24                                                        |
| 身份     | 登录的人                                      | 机器身份（服务账号）                                        |
| 挂了影响 | 这个人不能打印/扫描                           | 全公司不能远程打印                                          |
| 能力     | 本地打印、扫描件、读本地 Excel/图片、文件系统 | 拉任务、调驱动、回报状态、按设备路由                        |
| 形态     | GUI 托盘程序（Tauri）                         | 无界面服务（Node + 系统打印命令 / CUPS / Windows 打印 API） |

| 能力             | 说明                                                        | 为什么必须是壳                  |
| ---------------- | ----------------------------------------------------------- | ------------------------------- |
| 本地打印         | 调系统打印机，可选纸张/双面/份数                            | 浏览器打印对话框无法编程控制    |
| 扫描件与拍照入档 | 扫描仪 TWAIN / 相机                                         | 浏览器只有受限的 `getUserMedia` |
| 读本地文件       | 批量 Excel、客户发来的 PDF 报价单、样品照片文件夹           | 浏览器需逐个授权，批量体验差    |
| 离线暂存         | **只允许**暂存照片/草稿文本，回连后补录，**不允许离线出价** | 见下方风险                      |
| 本地缓存加速     | 样品图与目录缓存                                            | 展会/工厂弱网                   |

**为什么必须有桌面壳**：这是物理限制，不是偏好——浏览器拿不到系统打印队列、拿不到扫描仪、拿不到任意本地目录。所谓"将来浏览器可能支持"不能作为架构依赖。

**明确不做**：不做第二套业务界面（维护成本翻倍的经典死法）；不做离线报价（离线意味着"在没有账本的地方算钱"，本地草稿 + 冲突合并的成本与风险远高于收益，且违背铁律 1 的精神）。

**技术选择**：Tauri 优于 Electron（安装包小一个量级、不打包 Chromium、内存低）。这是**可变选择**（VAR-4），不是不变量。

**触发条件**：出现"必须打本地打印机"或"必须读本地 Excel/扫描件"的真实岗位需求。**在此之前不做。**

#### 3.3.4 移动端 · H5 `[0 / 规划]`

**先说清现状，别被 README 误导**：`apps/web` **不是 H5**。它是单页、无路由（`App.tsx:71`）、容器宽度 `max-w-[1180px]`（`App.tsx:34`）、三列按钮栅格 `sm:grid-cols-3`（`IntentBar.tsx:184`）、两列平铺的全景（`Panorama.tsx:127`）。`README.md:20` 与 `apps/web/package.json:5` 写着"Web + H5 按路由区分"，但仓库里既没有路由也没有移动布局——**"H5"目前是零**。

| 能力                       | 具体形态                             | 为什么在手机上                           |
| -------------------------- | ------------------------------------ | ---------------------------------------- |
| 审批（摘要 + 明细 + 改价） | 一屏一张卡，上下滑，批/驳/改三个动作 | P2 时延：老板在饭局上，晚 4 小时可能丢单 |
| 我的待办                   | 今天要批的、要跟的、要约的           | 随身                                     |
| 客户历史                   | 该客户最近报价、成交、寄样、偏好     | 见客户前 30 秒要看的东西                 |
| 拍照找样（T-001）          | 现场拍布样 → 出候选样品              | P1 现场性：只有手机在展会/客户桌上       |
| 寄样单现场录入             | 拍照 + 语音备注，**运单号允许后补**  | 跟单在快递点，纸上写单会丢               |
| 消息草稿发送               | 复制文案 / 生成图片 / 记录已发       | 报价批完就要发，人在外面                 |
| 通知落地                   | 点通知直接进该单据                   | 入口摩擦                                 |

**为什么先做 H5 而不是先做小程序或 App**：

- 迭代当天生效，**无审核**（小程序要审核，业务规则一改就要等）；
- 无包体限制（小程序主包 2MB）；
- 可直接复用 `packages/schema` 的契约与类型（这是唯一能跨端复用的东西）；
- 一套代码后续可以搬进 Taro 或企业微信 H5，不用推倒。

**必须标出来的三个硬前置**（不解决，H5 上线就是不可用的）：

1. **图片体积**：T-001 契约是 base64、上限 8MB（`packages/schema/src/tools/t001-search-fabric-by-image.ts:18`），服务端 JSON body 上限 10MB（`main.ts:13`）。手机原图 3–8MB，base64 后 ×1.37 → 必超。**先做客户端压缩或直传对象存储**，这不是优化项，是前置条件。
2. **请求层**：`apps/web/src/api.ts:34` 是相对路径 `fetch`，跨域 H5 需要绝对 base URL + token 注入。先抽 `packages/api-client`。
3. **身份**：审批必须来自登录态，现在是常量（`context.ts:12`）。**没有身份就没有移动审批**——否则等于把审批权发给任何一个拿到链接的人。

**不应该在 H5 上**：批量导入、模板编辑、成员权限、审计检索、全景宽表、任何"多列对比"的操作。手机上不做"看不全又要看清楚"的事。

**触发条件**：连续两周出现 ≥3 次"因为不在电脑前，审批/报价延迟超过 4 小时"。或者试点里有老板/主管明确要求。

#### 3.3.5 移动端 · 小程序 `[0 / 规划]`

**最重要的判断：内部小程序和客户小程序是两个产品，绝不能做成一个。**

**(a) 内部小程序（企业微信自建应用）`[0 / 规划]`**

| 能力              | 形态                                 |
| ----------------- | ------------------------------------ |
| 审批（批/驳/改）  | 同 H5 的审批，但入口在企业微信工作台 |
| 待办与提醒        | 企业微信消息卡片，点开直达单据       |
| 拍照找样 / 拍样品 | 复用小程序的相机能力                 |
| 快速查客户        | 只读摘要                             |

**为什么它和 H5 都要有**：不是因为功能不同，是因为**入口和通知不同**。H5 在微信里打开是"一个网页"，没有可靠的消息触达；企业微信应用有工作台入口和服务端消息推送。纺织公司的实际工作流就在微信/企微里，**能少切一次 App 就多一次使用**。

**技术现实**：小程序没有 DOM，`apps/web` 的 Radix + Tailwind 组件一个都复不了（`apps/web/package.json:13` 的依赖清单全是 DOM 组件）。**Taro 三端不等于省一次开发，等于 UI 重写一遍**——但 `packages/schema` 与 `packages/api-client` 可以完整复用，这是复用率的全部。

**不应该在内部小程序上**：模板管理、成员权限、批量导入、审计检索、全景宽表、任何表格编辑。

**(b) 客户小程序 `[不做]`**

理由见 1.6 第 1 条：客户活在微信聊天里，让他"打开小程序查报价"是把摩擦转给客户。正确形态是**输出格式**，不是一个端：

| 客户侧形态            | 说明                                                         | 现状         |
| --------------------- | ------------------------------------------------------------ | ------------ |
| 一页报价单 PDF / 图片 | 带公司抬头、型号、克重、单价、总价、有效期、付款方式、签章位 | `[0 / 规划]` |
| 只读报价链接（可选）  | 短链 + 签名 + 有效期，免登录，落地页只读，不能改任何东西     | `[0 / 规划]` |
| 寄样进度页（可选）    | 只读，物流状态 + 预计到达                                    | `[0 / 规划]` |

这三样东西在矩阵里占 `○`（降级形态），但它们**不是端**：没有登录、没有角色、没有回写路径。产品上要明确说"我们不给客户账号"，权限模型因此不用变复杂——这是本判断最大的工程价值。

#### 3.3.6 移动端 · App `[0 / 规划 → 判定不首选]`

**结论：现阶段不做独立 App。**

理由是一条一条算过的：

| App 独有的能力 | 是否真的需要 | 替代方案                                    |
| -------------- | ------------ | ------------------------------------------- |
| 消息推送       | 是           | 企业微信 / 小程序推送已覆盖                 |
| 离线作业       | 部分         | **只做"拍照暂存 + 回连补录"，不做离线出价** |
| 扫码           | 是           | H5 / 小程序调摄像头即可                     |
| 相机体验       | 是           | H5 已足够；小程序更强                       |
| 后台定位/轨迹  | 否           | 不做（隐私成本高、收益不明）                |

四项需求里三项被 H5 + 企微覆盖，剩下一项（真离线）在本项目的架构前提下**不应支持**（1.6 第 2 条同理：账本不能离开可信执行体）。所以 App 的边际价值不足以支撑一套新的构建、发布、审核、兼容维护。

**如果将来必须做**：用 Taro 从 H5 代码起（不是从 `apps/web` 起）。判断标准同样给死：**只有当"离线拍照暂存"被真实场景需要且 H5/小程序都无法满足时**才做。

#### 3.3.7 打印代理 `[0 / 规划]`

**定位**：把"打印"从"人在电脑前点一下"变成"系统在无人值守时也能打"。它是整个矩阵里唯一**不代表任何人**的端（机器身份）。

| 能力       | 说明                                                                  |
| ---------- | --------------------------------------------------------------------- |
| 注册与心跳 | 代理注册到服务端，报告在线、打印机清单、耗材状态                      |
| 拉取任务   | 长轮询或 WebSocket（不要公网回调：客户内网进不来）                    |
| 执行打印   | 只负责把服务端渲染好的 PDF 送去打印；**不做渲染、不做排版**           |
| 按设备路由 | A4 报价单 → 激光打印机；箱唛标签 → 热敏机（ZPL/TSPL，另一套排版逻辑） |
| 回报与重试 | `QUEUED / PRINTING / DONE / FAILED`，失败可重打，重打要留痕           |
| 本地排队   | 缺纸/离线时任务不丢，恢复后继续                                       |

**为什么渲染必须在服务端**：模板必须唯一。如果每个代理各自渲染，同一份报价单在不同机器上会不一样，而且模板里早晚会有人写业务逻辑——那等于在客户端复制了一份业务规则，绕过内核（铁律 1）。

**为什么代理必须独立于任何人的电脑**：挂在业务员笔记本上，他一合盖全公司打不出来。这条是运维常识，但非常容易在设计时被忽略。

**为什么先不做**：绝大多数"远程打印"需求的本质是"**导出 PDF 发微信**"。先做 PDF + 浏览器打印（零客户端），验证"格式个性化"是否真的被需要、需要到什么程度，再决定投入代理。**过早做代理的代价是：你要为一个还不确定的需求维护一套常驻进程 + 驱动兼容 + 客户现场运维。**

**触发条件**：每周 > 20 张单据需要人工打印/转发，**且**出现"没人值守但要出单"的诉求（仓库出库单、夜间自动打单），**或**出现箱唛标签需求（热敏，另一个世界）。

**格式个性化（模板）的归属**：模板管理是 **Web** 的能力（C15），渲染是**服务端**的能力（C06），打印执行是**代理**的能力（C16）。三者必须分开：业务员改模板不该碰打印，打印挂了不该影响模板。

### 3.4 每个端"不该有"的能力（防扩散清单）

这一节比功能清单更重要。**产品失控通常不是少做了什么，而是在错误的地方多做了什么。**

| 端             | 明确不允许出现                                                                 | 为什么                                                                 |
| -------------- | ------------------------------------------------------------------------------ | ---------------------------------------------------------------------- |
| **服务端**     | 业务界面；给管理员"直接调任意写工具"的面板                                     | 界面会在服务端长出第二套 UI 逻辑；写工具直通等于绕过 agent 与审批      |
| **Web**        | 拍照找样、扫码、离线作业、给客户看的只读页面（客户不该看到内部导航与权限体系） | 设备与场景不对；客户看到的必须是"输出格式"，不是"你的系统"             |
| **桌面壳**     | 第二套业务界面、离线出价、任何业务规则                                         | 双份 UI = 双份 bug；离线出价违背"账本不能离开可信执行体"               |
| **H5**         | 批量导入、模板编辑、成员权限、审计检索、全景宽表                               | 屏幕上做不完的事不要硬塞；这些都是桌前 5 分钟、手机上 50 分钟的事      |
| **企微小程序** | 同上 + 任何表格编辑、任何多列对比                                              | 小程序是"入口 + 通知 + 一键批"，不是小型 Web                           |
| **打印代理**   | 渲染、排版、业务判断、访问账本、代表某个用户                                   | 代理只是"手"，一旦它有判断力就会成为绕过内核的第二个入口               |
| **客户落地页** | 登录、编辑、任何回写、任何金额计算                                             | 只读 + 签名 + 有效期。客户侧一旦有回写路径，权限模型立刻复杂一个数量级 |
| **任何端**     | 计算金额、拼状态机、判定权限、直连数据库、缓存"可生效"的账本状态               | 见 3.6 跨端规则                                                        |

### 3.6 跨端一致性规则（六条，违反任何一条都会出现"两个真相"）

1. **契约唯一**：所有请求/响应/只读视图都来自 `packages/schema`，任何端不得自定义业务结构。
2. **金额只在内核算**：任何端都不得计算金额或总额（包括"预览时先算一下"），端的算术只允许格式化显示。
3. **状态机只在服务端**：端不得根据本地条件推演"应该变成什么状态"，只能展示服务端返回的状态。
4. **权限只在服务端判定**：端只决定"显不显示"，不决定"能不能做"。任何以"前端藏起按钮"实现的权限都是漏洞。
5. **审计只有一份**：不管从哪个端发起，`actor` 都必须是具名的人（或明确的机器身份），且落在同一条 `audit_log` 上。
6. **身份一套、登录方式多种**：账号与角色是同一份数据；Web 用密码/OIDC、企微用小程序的 `code2session`、桌面壳用设备码——但映射到同一个 user id。

### 3.7 端的解锁顺序与触发条件

把"端"从路线图改成触发器。理由：端的价值完全取决于使用场景是否真实存在，而场景存在与否只有**跑过真实业务**才知道。

| 顺序 | 端                      | 解锁触发条件（必须可观测）                                                         | 现状         |
| :--: | ----------------------- | ---------------------------------------------------------------------------------- | ------------ |
|  0   | 服务端 + Web            | 现在就在这里。先把"进 → 算 → 出 → 留痕"一条链跑通                                  | `[现状]`     |
|  1   | H5（移动审批 + 拍照）   | 连续两周 ≥3 次"因为不在电脑前，审批/报价延迟 > 4 小时"                             | `[0 / 规划]` |
|  2   | 打印代理 / PDF 出口闭环 | 每周 > 20 张单据需人工打印或转发；或出现箱唛标签需求                               | `[0 / 规划]` |
|  3   | 桌面壳                  | 出现"必须打本地打印机"或"必须读本地 Excel/扫描件"的岗位；或展会/工厂弱网场景被证实 | `[0 / 规划]` |
|  4   | 企微小程序（内部）      | H5 已在用，且被抱怨"每次都要找链接"；企业微信已是主工作流                          | `[0 / 规划]` |
|  5   | App                     | 前五端稳定运行 ≥ 3 个月，且"离线拍照暂存"被真实场景反复要求                        | `[0 / 规划]` |
|  —   | 客户小程序 / 客户登录端 | **不解锁**（见 1.6 第 1 条）；客户侧只做只读输出格式                               | `[不做]`     |

**两条硬规则**（写在这里是为了能在评审时直接引用）：

1. **同一时间只有一个端在开发。** 上一个端没有连续跑过真实业务一周，不许开下一个端。
2. **每个端上线前必须通过"一条端到端验收"**：一个真实角色，用真实数据，在这个端完成一件完整的业务动作，全程不碰命令行、不看开发者工具。做不到就不算上线。

## 4. 用户成功故事

写这一节的目的不是描述功能，而是让人读完能回答一个问题：**"我在为什么付钱？"**

**先把诚实规则说在前面**：每个故事分两栏——**今天**（当前仓库真实能做到的）和**之后**（依赖阶段一/阶段二的能力）。故事里出现的每一个系统动作，都标注了它依赖哪项能力、那项能力现在是什么状态。**没有任何一段把规划写成现状。**

四个角色，都来自纺织贸易公司的真实岗位：

| 角色     | 画像                                                  | 他在系统里的位置               |
| -------- | ----------------------------------------------------- | ------------------------------ |
| **陈立** | 业务员，34 岁，8 年，62 个客户，微信 4000 个联系人    | 派发意图 + 改稿 + 发送         |
| **老周** | 老板，52 岁，最怕两件事：报价报低了、业务员把客户带走 | 审批 + 全景                    |
| **小林** | 跟单，26 岁，每天在仓库和快递点之间跑                 | 寄样单 + 跟进                  |
| **王姐** | 客户，深圳面料采购，只用微信                          | 只接收东西，**永远不登录系统** |

---

### 4.1 陈立的一天 · 用之前（这就是今天）

**07:52** 地铁上，王姐微信："上次那块 220g 的，要 500 米，什么价？"
陈立回："我看下成本，一会儿给你。"

**08:40** 到公司。打开一个叫 `2025成本.xlsx` 的文件——这个文件有 7 个版本，他不确定哪个是最新的。找到那块布：成本 12.0 元/米。

**08:47** 微信问跟单小林："上次给王姐报多少来着？"
**09:10** 小林回："好像 15 块左右吧，去年的。"

**09:15** 陈立犹豫要不要报 15.2。他走到老板办公室，老周在打电话。他等了 12 分钟。

**09:29** 老周说："报 15.5，她这单急。"
**09:31** 陈立打开 `报价单模板-2024版.docx`，改客户名、改型号、改数量、改单价、改日期、改有效期。Word 的表格错位了，调了两分钟。

**09:41** 导出 PDF，截图，发微信。
**09:43** 王姐："能 14.8 吗？"
**09:44** 陈立又去问老周。

这一天，陈立报了 6 单价，成交 1 单。**没有一处留下"为什么报这个价"的记录。** 三个月后王姐再来问，同样的流程再来一遍，还是靠"好像 15 块左右吧"。

**今天这套系统在这段故事里的位置：没有位置。**

不是因为它不好，是因为它现在做不到这个故事里的任何一步：

- 系统能导入客户和样品（`apps/api/src/kernel/import.service.ts`、`POST /api/import`，`controllers.ts:87`），但**不能单条新建客户/样品**，也没有前端入口；
- 系统的"出报价草稿"按钮，单价是**成本底线 + 300 分死算出来的**（`IntentBar.tsx:59`），不是定价策略，所以它给不出 15.2 这个数；
- 系统批准后把状态改成 `SENT`（`quotes.service.ts:219`），但**什么都没生成、什么都没发出去**——没有 PDF、没有截图、没有发送记录；
- 系统看不到这个客户上次报了多少（`getDraft` 只允许读草稿，`quotes.service.ts:185`；T-003 连 HTTP 入口都没有）。

所以今天把它塞进这个故事，唯一的结果是陈立多了一个要打开的窗口。**这是必须承认的起点。**

---

### 4.2 陈立的一天 · 用之后（阶段一交付后的真实形态）

> 这一段依赖的能力：真实身份（`[0 / 规划]`）、agent 意图入口（`[0 / 规划]`）、定价策略（`[0 / 规划]`）、草稿详情（`[0 / 规划]`）、改稿闭环（`[0 / 规划]`）、PDF 导出（`[0 / 规划]`）、发送记录（`[0 / 规划]`）、客户历史（`[现状·残]`：工具存在但无 HTTP/UI）、回复议价识别（`[现状·残]`：规则引擎有 `CLASSIFICATION_RULES`，`platform/llm.ts:30`，但只在演示脚本里跑（`apps/api/scripts/demo-followup.ts`））。**每一项都还没做——这是交付目标，不是现状。**

**07:52** 地铁上，王姐微信："上次那块 220g 的，要 500 米，什么价？"

**07:53** 陈立没有回"一会儿给你"。他在手机上打开 H5，把王姐那句话原样粘进去，选客户「王姐」，点"出价"。

**07:53** 系统做完了过去 40 分钟里他做的所有事：

- 认出这是"报价"意图，不是"找样"也不是"寄样"；
- 拉出王姐的上下文：近 6 次成交价区间 14.8–15.3，最近一次 15.0（9 月 12 日），她从不接受第一口价但 3 天内会回，付款习惯是月结 30 天；
- 按定价策略算：这个品类底价 12.0，VIP 客户目标毛利率 12%，得出建议单价 **15.2**；
- 产出草稿 v1：数量 500 米、单价 15.2、总额 7600.00、有效期 15 天，**依据写着三行**——"该客户历史区间 14.8–15.3"、"上次成交 15.0"、"本次成本较上次 +2%"。

**07:54** 陈立看了一眼那个 15.2。他心里想 15.5（老周会说 15.5），但他在手机上，老周在睡觉。他改成 15.5，填理由"这单急"。

系统：草稿变 v2，重算总额 7750.00，记一条审计，同时把"改价 +0.3，理由：急单"写进王姐的决策增量。**这个动作今天不存在**——内核没有 `reviseDraft`，HTTP 面没有任何 PUT/PATCH。

**07:55** 他点"导出并发送"。系统生成一页报价单（公司抬头、型号、克重、500 米、15.5、总额、有效期、付款方式、签章位），存下"发给王姐、微信、v2、07:55"的记录，然后给他一段可以直接粘的文案 + 一张图。

**07:56** 王姐在微信里收到。她只用了 5 秒看懂：单价、总价、什么时候有效，她最关心的三件事都在第一眼能看到的位置。

**07:58** 王姐："能 14.8 吗？"

**07:59** 陈立把这句话粘回那张单据的对话区。系统识别为"议价"，出 v3：14.9，并附一行提示："低于 14.9 时毛利率 8.1%，低于本品类底线 10%——需要老板批。"（这是 `quotes.service.ts:88` 那条成本底线拦截的产品化表达，逻辑今天已有，提示界面还没有。）

**08:01** 陈立把 v3 标记为"需老板批"。老周手机上收到一条企业微信消息。

**一天结束时**，系统给他的小结是：报价 6 单、成交 1 单、平均改价幅度 2.1%、1 单触发底线保护、王姐这个月询价 4 次成交 0（平均价差 2.1%）。

**这一天和上一节最大的差别不是"快"**。是这三件事：

1. 他**一次 Excel 都没打开**，也**没有一次靠"好像 15 块左右"**；
2. 他改系统的建议的那两次，**变成了系统的记忆**（下次给王姐报价，依据里会出现"你上次改成 15.5，理由：急单"）；
3. 报价这件事第一次**有痕迹**：谁改的、改成多少、为什么、什么时候发给谁。

### 4.3 老周的一周 · 他看到什么

**用之前**：周五下午问"这周报了多少价、成了几单、哪单亏了"。答案来自三个人各自的印象，凑出来的数字他自己都不太信。有一单报价低于成本，是两个月后会计对账时才发现的——那单已经赔了。

**用之后**：周一早上，他打开 Web 的「业务全景」（今天已有只读聚合，`Panorama.tsx:127`；筛选、下钻、按毛利排序还没有）：

- 上周报价 37 单，成交 9 单，平均毛利率 11.8%；
- **3 单低于目标毛利被标红**，其中 2 单是他不知道的（一单是陈立自己批的，一单是新人报的）；
- 陈立上周改价幅度 2.1%，小李 7.4%（说明小李要么不会定价，要么在乱报）；
- 王姐这个客户：本月询价 4 次、成交 0、每次都在 2% 左右的价差上流失。

**老周真正买到的不是"报表"**，是三件事：

1. **防错**——"报价低于底线"从"靠人自觉"变成"系统挡"（内核已经有这条拦截，`quotes.service.ts:88`；他缺的是**看到它拦了几次**）；
2. **可见**——他能知道哪个业务员的定价在漂移，而不是等季度末看毛利；
3. **资产**——业务员休假、离职，客户的历史价和偏好还在系统里。这一条对他来说是"睡得着觉"的价值，比效率重要得多。

**一个具体的瞬间**（这是最容易成交的一刻）：某个周三，系统提示"这份报价低于成本底线，已拦截"。老周点开看了一眼：新人报了 11.6，成本 12.0。他想起上个月那单赔钱的事。**这一刻他明白了自己在为什么付钱。**

### 4.4 王姐的那一分钟 · 客户感受到什么

**用之前**：收到一张微信截图。图有点糊，要问"含税吗""多久有效""能不能开票"。她得把图片存下来，转发给她们财务。有时候图片过期了打不开。

**用之后**：收到一页报价单。她的公司名在最上面；型号、克重、成分、数量、单价、总价一行一行清楚；有效期写着"15 天内"；付款方式写着"月结 30 天"；底下是陈立公司的抬头和签章位。她不用问任何问题，长按转发给财务就能用。

**她感受到的是两件事**：

- **快**——从"什么价"到"能转发给财务的报价单"，10 分钟，而不是半天；
- **专业**——她能拿这份东西去见她的老板。

**一个重要的产品判断**：王姐的体验里**不该出现"AI"两个字**。她不需要知道这份报价是智能体起草的、陈立改了两次。对她来说，这就是"陈立他们的效率变高了、变专业了"。**任何让客户感知到"这是机器给的"的设计，都在削弱这份信任。** 所以客户侧永远不会是"一个端"，只会是"一个好看的输出"。

### 4.5 小林的一单 · 阶段二之后（跟单视角）

**用之前**：仓库里手写一张寄样单，拍照发群。运单号抄在纸上。第三天客户没回，谁都不记得该催。客户回"这个多少钱"，小林把微信截图转给陈立，陈立再走一遍 4.1 的全流程。

**用之后**（依赖能力：跟进图的 HTTP 入口与待办列表，`[0 / 规划]`——图本身是完整的，`followup-graph.ts:279`）：

**周二 16:20** 小林在快递点，用手机拍寄样箱、扫运单号，选客户「王姐」、样品「220g 棉」，点提交。运单号当场有；如果没扫上，允许后补（现在的做法是**让业务员编一个运单号**，`IntentBar.tsx:91`，然后拿着这个假号去"追踪"——这是必须修掉的）。

**周五 10:00** 系统提示："王姐这批样已签收 3 天，未回复。建议今天上午微信跟进，话术如下……" 小林看了一眼，改了两句，点"已发"。

**周五 20:41** 王姐回："这个 500 米什么价？" 小林把这句话粘进系统，图自动走到"客户询价 → 生成报价草稿"，一张 DRAFT 报价直接出现在陈立的审批队列里。

**小林这一天的变化**：他不再需要"记得催"，系统记得；他也不用当"人肉中继"，客户的一句话直接进到报价环节。

### 4.7 价值账（口径 > 数字）

**这一节只给算法，不给承诺。** 任何具体的钱数都必须由试点校准，写死数字等于骗人。

**① 工时口径**（最容易被验证的一条）

```
节省工时/人月 = (现状单耗时 − 之后单耗时) × 日均单数 × 月工作天数
             = (25 分钟 − 7 分钟) × 6 单 × 22 天
             ≈ 39.6 小时/人月
```

注意：**这 39.6 小时不等于 39.6 小时的可计价收入**。业务员空出来的时间如果只是刷手机，价值为零。所以真正的口径应该是"同样的人力能接多少单"——这一条必须靠试点测量，不能靠推算。

**② 防错口径**（老板最能感知的一条）

```
单次漏底损失 = 单价 × 数量 × 漏底比例
             = 15.0 元 × 500 米 × 3%
             = 225 元/单
```

一个月拦下 2 单，就是 450 元的直接毛利保护。金额不大，**但心理价值极大**——因为它证明"系统在替我看住我没时间看的地方"。这是最容易触发第一笔付款的价值。

**③ 客户流失口径**（最难量化、最容易被忽略的一条）

王姐这个月询价 4 次、成交 0、平均价差 2.1%。如果系统能在第 3 次时就提示"这个客户连续 3 次因 2% 流失"，一次挽回的订单可能就是几千元。**这条价值只在有历史数据之后才存在**——这也是为什么"客户上下文"是护城河，而不是"功能多"。

**④ 交接口径**（离职场景）

一个业务员离职，60 个客户、几百次历史报价、无数条"这个客户在意什么"。用之前：跟着人走。用之后：在系统里。**这一条不需要精算，老板一听就懂。**

### 4.8 三个成交场景（谁在什么时候决定付钱）

产品能不能卖出去，往往不取决于"功能全不全"，取决于**有没有出现那一个时刻**。这三个时刻是可设计的：

| 场景   | 触发时刻                                               | 谁做的决定     | 对应产品主线                       |
| ------ | ------------------------------------------------------ | -------------- | ---------------------------------- |
| ① 防错 | 系统第一次拦下一份低于成本底线的报价，老板点开看了一眼 | 老板           | 成本底线 + 审批详情 + 异常看板     |
| ② 交接 | 业务员休假一周，公司照常给她的客户报了 3 次价          | 老板（或主管） | 客户上下文 + 归属与权限 + 历史可见 |
| ③ 产能 | 旺季一天 20 单报价，没人加班到十点                     | 业务员自己推动 | 意图入口 + 草稿质量 + 一键发送     |

**注意 ③ 的推动者是业务员，不是老板。** 这是这个产品的一个反直觉之处：**它先被一线爱上，再被管理层买单**。所以试点里最先要给的是"让业务员省事"的能力（出价快、不用做 Word、不用问历史），而不是"让老板看见"的能力（看板、审计）。**顺序反了，试点会死在一线抵制上。**

## 5. 目标与做法沉淀

### 5.1 不变量（INV）—— 长期守住，改动必须先改本文

判断标准：**违反它，产品就不再是这个产品**。

| 编号   | 不变量                                                                        | 为什么必须守                                           | 违反的后果                                         | 可验证点（现在就有）                                   |
| ------ | ----------------------------------------------------------------------------- | ------------------------------------------------------ | -------------------------------------------------- | ------------------------------------------------------ |
| INV-1  | 业务表只有一个写入口：确定性内核；其他层不得触达数据库                        | 责任可复算、可定位                                     | 账本出现"查不清怎么来的"数据                       | `eslint.config.mjs:64`、`test/boundary.test.ts`        |
| INV-2  | 智能体产出永远是草稿/建议；生效必须有人类的具名动作                           | 责任不可转移                                           | 第一次错价就摧毁信任                               | `quotes.service.ts:207`、`shipments.service.ts:151`    |
| INV-3  | 每个业务能力只以 Tool 契约暴露；agent 不操作界面                              | 契约可审计、可组合、可回归测试                         | 能力退化成"教 AI 点按钮"，脆弱不可测               | `tools/index.ts:32`、`packages/schema/src/tools/*`     |
| INV-4  | 人类的决策面只有三个：派发 / 审批 / 全景；功能增长不新增决策面                | 界面成本 ≈ 常数，这是形态的经济性根基                  | 退化成"带 AI 按钮的传统 SaaS"                      | `App.tsx:10`（当前三个，措辞见 5.3）                   |
| INV-5  | 金额只在内核用整数计算，任何端不得计算或传入汇总                              | 钱的算术不能有第二种真相                               | 前后端算出两个总额，审计无意义                     | `kernel/money.ts`、`quotes.service.ts:98`              |
| INV-6  | 输入契约 `.strict()`，未知字段一律拒绝                                        | 防止"夹带账本字段"（如 `status`、`version`）           | 客户端可伪造状态流转                               | `packages/schema/src/*`                                |
| INV-7  | 每一次业务写入必须同事务写审计；审计只能追加                                  | 事后能回答"谁、何时、改了什么"                         | 争议时无法举证                                     | `kernel/audit.ts:28`、`0001_audit-append-only.sql`     |
| INV-8  | 报价/单据的对外发送必须留痕（发给谁、哪一版、何时）；不得在未发送时写"已发送" | 账本不能与事实不符                                     | 用户第一次信任就被打破（当前 `SENT` 正是这个错误） | `quotes.service.ts:219`（**当前违反，阶段一必修**）    |
| INV-9  | 客户数据默认归属到人（`own`），共享需显式授权                                 | 客户是业务员的私产；不归属就没人录入                   | 系统拿不到真实数据，整条链失效                     | `customers` 表无 `ownerId`（**当前违反，阶段一必修**） |
| INV-10 | 一个能力只有一个权威端；其他端只允许降级形态                                  | 两套实现必然两套口径、两倍 bug                         | 出现"两个真相"，用户体验到不一致                   | 本文 3.2 / 3.5                                         |
| INV-11 | 模板只能引用内核视图变量，不得含业务逻辑                                      | 否则模板即业务逻辑，绕过内核                           | 同一份单据在不同模板下算出不同金额                 | `[0 / 规划]`，做模板时先立这条                         |
| INV-12 | 外部世界接入点必须有人工兜底通道，且兜底动作要留痕                            | 渠道审批慢、接口会挂；"假装成功"比"承认没做"危险一百倍 | `SENT` 式谎言反复出现                              | `[0 / 规划]`                                           |

| VAR-2  | LLM provider       | `local-rule`（规则引擎）           | 任何真实模型（实现 `LlmProvider`）              | 有 key 且预算到位               |

### 5.3 与既有文档的对齐与订正

本文是上位文档。以下五处**本文推翻或收紧了既有文档的说法**，其余一律不变；工程细节仍以那三份为准。

**订正 1 · 铁律 #4 的措辞：从"三个窗口"改为"三个决策面"**

- 原文（`README.md:252`、`App.tsx:98`）："人类界面只有三个窗口 · 不做逐条录入表单"。
- 改为：**人类界面只有三个决策面（派发 / 审批 / 全景）；决策面数量固定，端数与页面数不受此限。**
- 理由：在多端形态下，"三个窗口"字面禁止 H5 与小程序（它们物理上装不下三个窗口），会让人误以为"上移动端=违反铁律"。真正的约束是**决策面**：不管在哪个端，人都只有这三种参与方式。约束不变，表述精确化。
- 影响：不改变任何已实现代码；改变评审时的判断口径。

**订正 2 · "桌面壳"与"打印代理"是两个产物，不是一个**

- 原文（`platform-and-engineering-plan.md` Q2 与 Q6-B）：桌面壳"只做本地桥（打印/扫描/读文件）"，打印代理"跑在办公室常驻机器上"——两处都归入"客户端/桌面端"，没有区分。
- 改为：**桌面壳（个人、随人开关、GUI、登录的人）** 与 **打印代理（常驻、7×24、无界面、机器身份）** 是两个独立产物，部署方式、身份模型、失败影响完全不同（见 3.3.3 的对照表）。
- 理由：混为一谈会导致两个工程错误——把代理做成 GUI 装在某人电脑上（他一关机全公司打不出单），或把壳做成常驻服务（升级与权限问题）。
- 影响：Q2/Q6 的结论方向不变，但交付物清单需要拆成两条。

**订正 3 · 端从"阶段"改为"触发条件"**

- 原文（`usability-roadmap.md` 阶段表、`platform-and-engineering-plan.md` Q8）：移动端"阶段三之后"、桌面壳"阶段二"。
- 改为：**端由可观测的触发条件解锁**（见 3.7），而不是由时间阶段决定；并加一条硬规则"同一时间只有一个端在开发"。
- 理由：阶段是时间承诺，触发条件是事实承诺。端的价值取决于场景是否存在，而场景是否真实存在只能靠跑过的业务证明。**当前执行顺序不变**（仍是先 Web 链路），变的是判断依据。
- 影响：不改变近期计划，改变了"什么时候该开下一个端"的决策方式。

**订正 4 · 客户侧不做"端"，只做"输出格式"**

- 原文（`platform-and-engineering-plan.md` Q1 待拍板第 3 条）：把"小程序是否面向客户"列为待用户拍板的商业问题。
- 改为：**本文判定客户侧不做登录端**（客户小程序 / 客户 Web 登录页均不做），只做只读输出（PDF / 图片 / 签名短链）。理由：纺织客户活在微信里，让客户注册登录是把摩擦转给客户；且客户侧一旦有回写路径，权限模型立刻复杂一个数量级（见 1.6 第 1 条、3.3.5）。
- 理由：这不是商业判断，是产品形态判断——它有明确的技术后果。**如果用户另有商业理由要客户自助端，可以推翻本节，但要同时接受权限模型的成本。**
- 影响：删掉一类高成本规划，把"客户体验"落到"输出质量"上。

**订正 5 · "报价出口"不等于"导出 PDF"**

- 原文（`platform-and-engineering-plan.md` Q6-A 与分期表）：阶段一做"报价 PDF 导出"。
- 改为：**出口 = 可转发形态 + 发送记录 + `SENT` 语义修正**，三者同批；只导出文件不算出口。
- 理由：现在的 `SENT` 是假发送（`quotes.service.ts:219`），如果只加 PDF 而不加留痕，错误只是从"什么都没发却写已发送"变成"发了但不知道发的是哪一版"。INV-8 必须一次性立住。
- 影响：阶段一的范围从"导出"扩为"导出 + 留痕 + 语义修正"。

**事实性纠正（顺手记下，避免后续重复劳动）**

- `docs/usability-roadmap.md` 写于第六步之前，其中"若坚持零录入表单，就必须先做 Excel/CSV 导入"的暗示已过时：**导入已实现**（`apps/api/src/kernel/import.service.ts`、`POST /api/import`，`controllers.ts:87`、`pnpm seed`）。当前缺的不是"批量导入"，而是"单条编辑"与"前端入口"。

### 5.5 这份文档的维护规则

**什么时候必须改本文（而不是改别处）**：

1. 新增一个端，或改变某个能力的权威端 → 改第 3 节与 3.5 表；
2. 任何 INV 需要放宽 → 先在 5.1 写清"为什么可以放宽、代价是什么"，再动代码；
3. 1.6 中某条"做不成"被证伪 → 直接改该条并附证据，不要悄悄删；
4. 1.3 的某个假设被验证或推翻 → 把该行从"假设"移到"已验证"或"已推翻"，并写日期；
5. 与另外三份文档出现冲突 → 冲突记在 5.3，本文优先，但**必须写理由**。

**怎么用这份文档防跑偏**（给评审用的三个问题）：

- 这个需求属于哪个决策面？如果三个都不是，它大概不该做成界面。
- 它落在哪个端？是不是已经有权威端？如果有，为什么要在第二个端再做一次？
- 它违反哪条 INV？如果一条都不违反，那它可能只是实现细节，不需要讨论。

## 附录 B · 术语

| 术语        | 含义                                                                        |
| ----------- | --------------------------------------------------------------------------- |
| 内核 kernel | 唯一能写业务表的确定性代码层；不含 AI                                       |
| 工具 Tool   | 智能体唯一可调用的业务能力接口，有 Zod 契约与可判别错误码                   |
| 草稿 Draft  | 智能体或人产出的未生效单据，必须人类 confirm 才流转                         |
| 决策面      | 人类参与业务的三种方式：派发、审批、全景（不是"窗口数量"）                  |
| 权威形态    | 某个能力唯一允许"做全"的端；其他端只允许降级形态                            |
| 降级形态    | 只读、摘要、受限动作。允许存在，但不得产生第二套业务逻辑                    |
| 决策增量    | `customer_contexts.decision_deltas`：人每次修改建议的记录，产品护城河的原料 |
| 输出格式    | 给客户看的东西（PDF/图片/只读链接），**不是端**，不带登录与回写             |
